# 桌面功能接口逆向

## 目标与边界

交付有明确契约的 **Functional API**，而非一次抓包重放。T1（脱离目标客户端）优先但非硬门槛；T2（客户端运行时直接调用内部函数）通过工程验收也合格。分析阶段可人工或 UI 自动化建立基准；交付调用链禁止坐标、图像、键鼠、DOM 点击与 UI 事件模拟。CDP 调业务函数是否合格取决于其实际调用链，不取决于工具名字。

仅使用任务相关样本与明确提供的测试环境。保持原文件不变；不安装插件、不修改系统设置，不包含防护绕过、凭据提取或恶意操作。缺少必要观测能力时记录阻碍及证据，使用现成诊断/开发接口或测试构建。

## 开工顺序

1. 阅读当前技能与 MCP/tool 目录，仅加载本次需要的技能。先核实实际可用工具、参数与版本；无匹配则用文件工具，别假定 MCP 已安装。
2. 从 [研究记录模板](templates/research-record.md) 创建任务记录，明确功能、输入、可独立确认的成功效果、预算及测试环境；恢复任务时先读记录及失败证据。
3. 阅读 [目标与证据](references/01-goals-evidence.md)、[观测与定位](references/02-observation-routing.md)，建立基准并逐个改变变量，定位完整调用链与实际通道。
4. 按实测选择 T1/T2：协议与状态参考 [协议契约](references/03-protocol-contract.md)；内部函数参考 [T2 适配](references/04-internal-call-adapters.md)。不以算法稳定推导容易逆向；内部函数调用相关结构往往比底层算法变化更频繁，维护成本必须按版本测量。
5. 用 [接口契约模板](templates/interface-contract.md) 固化输入、输出、错误、状态、认证依赖、生命周期与并发边界；凭据通过宿主合法会话机制在运行时提供，记录中只保留占位符。
6. 按 [可靠性与验收](references/05-reliability-acceptance.md) 执行参数化、重连、重试幂等、版本回归与清理检查，填写 [验证矩阵](templates/validation-matrix.md)。未执行的测试标记为未验证。

## 必须遵守的判断规则

- 将 OBSERVED（观测）、HYPOTHESIS（假设）、VALIDATED（限定条件验证）分开；附版本、步骤、证据与限制。文献结论不继承为当前实测结果。
- 超时不等于失败；副作用结果未知时先查询/对账，缺少幂等保障就停止自动重发。
- 识别 ABI、地址定位、对象生命周期、线程与运行时上下文；未知版本默认停止调用并要求适配验证。
- 不承诺 T2 低维护、T1 无限并发、自动认证恢复或某工具普适可用。登录需要交互时暴露 `AUTH_REQUIRED` 并说明运维前置条件。
- 最终报告包含：路线及依赖、契约、证据索引、通过/失败/未测清单、已知限制、版本支持与回滚办法。仅有一次成功不算稳定接口。
