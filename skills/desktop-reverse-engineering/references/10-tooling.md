# 10 · 工具怎么用（定位阶段）

> 一句话：**工具缩短的是「定位」，不是「决策」。**
> 方法答"该看哪里"（01/02/07），工具答"多快拿到那个地址、那段明文、那个结构体"。
> 一个工具在手上只该有三种用途，分不清就别打开它：**看**（观测）、**停**（下断、看现场）、**改**（patch / hook）。

## 10.1 选型矩阵（先问要什么，再选工具）

| 你要什么 | 首选 | 次选 | 别浪费时间的做法 |
|---|---|---|---|
| 拿 HTTP 明文 | 客户端日志函数 hook | 进程内 `SSL_write`/`send` hook | 系统代理 + 证书（前端型常直接无视） |
| 定位「哪个函数发出的请求」 | 动态调试器下断 + 栈回溯 | 静态交叉引用（xref） | 二进制里搜 URL 字符串碰运气 |
| 看清一个对象/结构体 | 调试器内存窗口 + 偏移推算 | ReClass 类工具 | 纯猜字段顺序 |
| 验证「这函数到底有没有被调」 | 动态调试器一次性断点 | Frida `Interceptor` 打日志 | 读代码脑内推演 |
| 要能重复跑 100 次 | Frida + Python 脚本 | 调试器脚本 | 手点调试器 |
| 改行为验证假设 | Frida（可回滚、可复用） | 调试器 patch（一次性） | 直接改磁盘文件（先查完整性校验） |
| 判断有没有壳 / 什么壳 | 壳识别工具 + 段表 + 入口特征 | 手工看 PE 段 | 上来就脱 |
| 找本地 IPC / 配置文件 | 文件与注册表监视 | 句柄/管道枚举 | 猜路径 |
| 确认「到底有没有发包」 | 抓包看流量大小与时序 | 进程内 socket hook | 用抓包工具读明文（加密时读不到） |

**顺序纪律**：观测类（日志 / hook）→ 定位类（调试器）→ 静态类（反编译器）→ 改写类（Frida）。跳步的代价通常是"工具能跑，但结论不可复现"。

## 10.2 动态调试器（x64dbg / WinDbg 一类）

### 什么时候真的该开

- 需要**运行到某处的现场**：寄存器、栈、`[this+0xNNN]` 的字段值。
- 静态拿不到交叉引用（虚调用、函数指针表、RTTI 不可达）。
- 要确认"这函数被谁调、参数是什么"。
- 要在改代码之前，先确认**这条路径真的会被走到**。

### 什么时候别开

- 只是想抓 HTTP/WS 明文 → 先做日志 hook，成本低一个数量级。
- 目标有反调试或虚拟化壳 → attach 就被踢，改走"边界观察"或 hook。
- 目标是**长期复用** → 调试器是探索工具，脚本才是交付物。

### 操作配方

| 目的 | 做法 | 注意 |
|---|---|---|
| 附加 | 先让目标进入目标界面，再 attach | 位数要对应（32 位进程用 32 位调试器）；关掉"入口点即断" |
| 跳到函数 | 用 `模块名+偏移`（RVA），不要用绝对地址 | ASLR 打开时绝对地址每次都变；结论里只写 RVA |
| 下断点 | 普通断点 / 硬件断点（数量有限）/ 内存断点（盯字段被读写） | 字段级追踪用内存断点，比满屏指令断点高效 |
| 条件过滤 | 断点加条件（如 `[esp+8]==0x1f`）或限定线程 | 渲染/心跳线程命中太频繁会把调试器拖死 |
| 看调用现场 | 栈窗口 → 调用栈 → 双击返回地址看 caller | 按调用约定读参数：`ecx` / `[esp+4]` / `[esp+8]`（x86 thiscall） |
| 展开结构体 | 把 `[reg+偏移]` 丢进内存窗口，跟随指针逐层展开 | 先记下偏移表，再回静态确认字段类型 |
| 留证据 | dump 到文件 / 复制 hex，落盘进 evidence 目录 | **截图不算证据**；hex + 时间戳 + 版本号才算 |

### 常见坑

- attach 后程序卡死：断点命中在 UI 线程；先禁用断点让程序跑起来，再单点启用。
- 断点"从没命中"：先确认目标代码真的在跑（换个必然命中的位置试探），别急着改地址。
- 64 位调试器打不开 32 位进程：位数选错，不是权限问题。
- 调试器里一切正常、脚本里就失败：调试器改变了时序（尤其注入/加密初始化阶段）。

## 10.3 Frida（把一次性发现变成可复用脚本）

安装与卸载前读 [12 · 采集器生命周期](12-instrumentation-lifecycle.md)：同一目标由一个 owner 串行管理，保留 pending 操作；以 API 完成而非仅状态属性确认清理。具体 listener/onLeave 行为按已安装版本核对。

- **定位用途**：`Interceptor.attach` 打点、`onEnter` 读参数、`Memory.readByteArray` 取结构体、`NativeFunction` 直接调内部函数（T2）。
- **和调试器的分工**：调试器负责"找到"，Frida 负责"跑一万次"。
- **坑（都真实踩过）**：
  - API 跨版本改名/移除：注入前先打印当前版本可用方法，别照抄旧脚本。
  - 宿主与目标位数不一致 → attach 失败或读内存全 0。
  - 指针/地址参数传十进制还是十六进制要看清，传错不报错、只是静默读到垃圾。
  - **注入的结构体本身要被保活**（放进 keep 数组），否则被 GC 回收后你注入的明文变垃圾——表现为"服务端说参数非法"，方向会带偏十几轮。
  - 目标有反注入/完整性校验时，先做内存 patch 而不是改文件。

## 10.4 反编译器（IDA / Ghidra）

**别一上来全量反编译**。200 MB 单体、几万个函数，几小时也出不来结论。

正确顺序：

1. 字符串 / 导出表 / RTTI 名 → 定位 2~3 个候选函数
2. 只反编译这几个函数 + 它们的直接调用者（两跳以内）
3. 需要理解字段语义时，再顺着结构体用法回到动态侧验证
4. 签名/加密类算法：静态读结构 + 动态对输入输出，两边夹

选型：IDA 的 F5 与调试器联动更顺；Ghidra 脚本化与免费更适合批量。**工具差异远小于"先定位再反编译"这条纪律的差异。**

## 10.5 抓包工具（什么情况下它们才是答案）

| 工具 | 能回答 | 不能回答 |
|---|---|---|
| 代理类（mitmproxy / Charles 等） | 目标**愿意走系统代理**且无证书固定时的明文 | 前端型壳无视系统代理；做了固定的连接 |
| 抓包器（Wireshark 一类） | 有没有发包、包多大、时序、连接复用 | 加密内容的语义 |
| 进程内 socket hook | 加密前的明文、明文长度 | 上层业务字段含义（要回到结构体） |

**判据**：抓包看不到东西时，先怀疑"通道判断错了"（回 02），而不是"证书没装对"。这条错判能烧掉半天。

## 10.6 低成本高收益的小工具

| 用途 | 工具类型 | 备注 |
|---|---|---|
| 判壳 | 壳识别 + PE 段/入口特征 | 结论直接影响路线（壳四分类见 01） |
| 导出/符号 | `dumpbin` / `objdump` / `strings` | 找模块、找日志格式串、找 RTTI 名 |
| 文件与注册表行为 | 文件系统监视器 | 找日志落盘位置、配置文件、命名管道 |
| 进程内情 | 进程/句柄查看器 | 看加载模块、线程栈、句柄类型 |
| 结构体还原 | 内存 dump + 偏移表 | 配合调试器内存窗口 |
| 前端资源 | 打包文件解包 | 前端型先拿 bundle，再 grep 调用点 |

## 10.7 两套典型组合（按客户端形态）

**前端型（CEF/Electron）**
```
CDP 打开 → 找传输层封装 → bundle 里 grep 调用点
  → 代理类对照一次真实请求形状 → Frida hook 前端桥函数（可选）
```

**原生单体型**
```
壳识别（有壳先分类，不破）
  → strings / RTTI 定位候选
  → 动态调试器下断，确认调用现场与参数布局
  → Frida 脚本化复现（同参数能重复成功）
  → 离线复算加密/序列化，验证"我理解的格式"与"线上字节"一致
```

## 10.8 什么时候该换工具（硬信号）

| 信号 | 换向 |
|---|---|
| 同一个地址找了 3 次没找到 | 停止动态试错，转静态定位（或反过来） |
| 断点命中太频繁 / 程序卡死 | 改 hook 或加条件过滤，别硬撑 |
| 抓包看不到任何请求 | 回通道判断（02），不是换抓包工具 |
| 工具里能跑、脚本里不行 | 查时序与初始化，别怀疑协议 |
| 结论只能复现一次 | 回方法层：变量没控制住 |

## 10.9 记录要求（配合 08）

每个工具动作产出三样，缺一不算做完：

1. **可重放的命令/脚本**（含版本、参数、目标版本号）
2. **落盘的原始输出**（hex / 日志切片 / dump 文件），不是截图
3. **一行结论**：这次动作确认了什么、排除了什么

> 工具越强，越容易产出"看起来是证据"的东西。判据仍是：**换参数能复现，且能被第二份独立证据支持。**
