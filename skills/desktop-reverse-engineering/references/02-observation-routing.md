# 02 · 观测、工具选择与调用链定位

## 先盘点，后使用

1. 阅读宿主实际暴露的 skills、MCP 与文件工具目录。记录可用工具的名称、版本、参数 schema、输入范围和输出格式。
2. 按问题选能力：本地文本优先 read/glob/grep；模块分析选择已具备的 PE/ELF/Mach-O 查看器；网络选择现有诊断记录；运行时选择应用已开放的调试接口或测试构建。不要为了写文档安装插件。
3. 只有任务需要真实浏览器观测时才加载对应浏览器技能；文档整理不因提及 CDP 就加载浏览器工具。无匹配工具时写明能力缺口，先做文件层分析。
4. 记录工具失败及影响，分辨版本不匹配、权限、网络和参数错误；不把单次失败归纳为该框架全部失效。

## 建立架构图

仅查看目标相关进程及样本：主进程/子进程职责、模块依赖、前端资源、已开放日志与本地服务。命令行可能含私密数据，采集前设计过滤规则。静态导入不覆盖动态加载，模块名也不证明实际功能；用运行证据核对。

建议图式：`调用者 → UI/前端 → 业务层 → 传输/IPC → 服务或持久化层`。真实应用可以多层、多通道或完全本地执行，日志只是一个可选观测源。

## 基准与差分

- 以测试资源完成一次功能，记录时间窗口、输入、预期副作用、实际效果。
- 每次只改变一个变量：内容长度、类型、目标对象、状态、连接时机；保留空操作对照。
- 用关联 ID、时序、数据摘要交叉关联日志、函数与网络；相近时间只是关联线索，不直接等于因果。
- 区分前置上传、提交、确认、异步事件、缓存刷新等步骤；不要把上传成功当业务操作完成。
- UI 分析可以帮助触发行为，但最终接口在无 UI 自动化控制下重新验收。

## 按证据辨别通道

| 候选通道 | 可观察信息 | 仍需验证 |
|---|---|---|
| HTTP/HTTPS | 方法、路由模板、状态码、请求/响应关联 | 认证依赖、异步完成、分页和错误语义 |
| WebSocket | 握手、子协议、帧方向及事件 | 帧与业务消息关系、心跳、断线续订 |
| TCP | 连接生命周期、读写数据、时序 | framing、字节序、拆包粘包、关联 ID |
| UDP | 数据报边界、源/目的、序号 | 丢包/乱序/重复、应用确认、分片重组 |
| IPC/RPC | 命名管道、Unix socket、COM/RPC 或共享内存接口 | 权限、锁、对象/句柄生命周期、进程重启 |
| 本地文件/数据库 | 测试副本的 schema、变更、事务 | 文件变化是否完成业务，缓存/锁与一致性 |

二进制长连接不自动等于 WebSocket；日志里出现 URL 不证明它已发送；文本、附件、实时事件可能走不同通道。观测点覆盖范围须记录。

## 观测约束

优先使用现有诊断、源码、开发接口、测试构建或可回滚观测点。保留应用行为及副作用：即便日志函数返回 void，也可能涉及锁、状态、审计或时序，不能据此省略原行为。量化观测开销与丢事件情况。

对未开放的调试功能或保护限制，记录条件并停止该候选路径；本文不包含禁用校验、反调试规避、启动器替换或注入绕过方案。所有研究变更都应可恢复，原始样本与派生产物分开。
