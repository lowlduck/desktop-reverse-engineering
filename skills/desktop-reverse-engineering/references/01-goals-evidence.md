# 01 · 目标、证据与路线优先级

## 交付等级

| 等级 | 运行形态 | 验证重点 |
|---|---|---|
| T0 | 人工/分析工具完成基准操作 | 功能存在、前置条件及可核对的实际效果 |
| T1 | 不依赖目标客户端运行 | 停止相关客户端及其辅助依赖后仍完成测试，明确剩余服务依赖 |
| T2 | 客户端运行，直接调用业务函数/内部服务 | 接口契约、客户端状态、ABI/上下文、版本适配 |
| 非交付 | UI 自动化驱动功能 | 仅供研究与基准对照，不作为最终接口后端 |

T1 的「脱离客户端」不等于不联网、不认证或任意平台可运行。本地独立服务若仍需厂商辅助进程，必须声明依赖。T2 可作为正式交付，但不因「调到了函数」自动合格。

## 路线优先级（按性价比，不按先进程度）

```
① 日志侧信道 hook          ★★★★★  一次拿到 URL + Body + 错误码
② 前端 bundle 静态读        ★★★★★  参数/枚举/签名算法常在这里明文
③ 页面内部函数（CDP）       ★★★★   能「调而不破」，签名复用
④ 自研 HTTP 层 vtable hook  ★★★★   能拿 URL+Body，注意覆盖不全
⑤ 本地数据库 / 缓存         ★★★    只读测试副本
⑥ 内存扫描                  ★★     兜底：凭据、请求体
⑦ 破壳 / 逆算法             ★      只有当「必须静态理解算法」且「无法调用」时
```

判断依据是 ROI，不是技术含量。案例中 60% 的时间被花在备选方案（系统代理、Frida、替换 DLL）上，真正的突破在最后 1 小时的日志 hook。

## 壳四分类（先分类，再决定破不破）

| 类型 | 代表 | 可破性 | 处置 |
|---|---|---|---|
| 压缩壳 | UPX / ASPack / MPRESS | 容易 | 直接脱，分钟级 |
| 加密壳 | ASProtect / Enigma / PECompact | 可破 | 跑到 OEP → dump + 修 IAT |
| 虚拟化壳 | VMProtect / Themida | 不能「还原」 | **不脱**，走边界观察或直接调用 |
| 硬件绑定 | 商业壳 | 换机不可用 | 评估是否值得继续 |

虚拟化壳的本质是「原指令被编译成 VM 字节码」，原函数体已不存在；成本从小时级升到天/周级且随版本重来。因此默认动作是**改观测点**，而不是破壳。

判据：`.vmp0/.vmp1` 段名、函数开头是随机字节、反汇编器给不出有效指令、动态工具 attach 后被踢。

## 时间盒与熔断（写进研究记录）

| 阶段 | 预算 | 到点仍未通过怎么办 |
|---|---|---|
| 侦察 | 30 min | 至少产出架构图与候选通道，不许无结论继续 |
| 单条路线 | 45 min | 记「已排除 + 错误码」→ 换下一条 |
| 同一路线失败次数 | 3 次 | 强制换路线，禁止第 4 次硬试 |
| 单目标总预算 | 见记录 | 触发即降级交付（T1 → T2）并告知需求方 |

熔断不是放弃，是防止把预算烧在「看起来该用」的方案上。

## 范围收敛

写清目标操作、支持的数据类型、目标对象、输入范围、账号权限前置、平台与版本、允许的副作用、耗时与资源预算。高复用是**约定范围内**的参数化，不要求一个接口实现所有业务功能。状态要显式建模，不追求伪「无状态」。

## 证据标签

| 标签 | 使用条件 |
|---|---|
| OBSERVED | 直接看到的现象，保留时间、版本、工具、脱敏证据引用 |
| HYPOTHESIS | 对现象的解释，列替代解释与可证伪实验 |
| VALIDATED | 在明确版本/输入/环境范围通过可重复实验，列次数与失败样本 |
| PARTIAL | 仅局部路径通过，缺项明确 |
| REJECTED | 假设被实验推翻，记录原假设与反例 |
| UNTESTED | 尚未执行，不赋予通过状态 |

双层证据：**调用受理** + **业务结果**。HTTP 200、函数返回 true、队列入列、界面提示都可能是受理。用测试资源查询、事件回执、目标状态变化做第二份证据。

「没有抓到」只说明当前观测点未捕获，不证明应用没有该通道；失败也不自动证明存在某种保护。工具错误原文与原因推断分栏写。

## T1 / T2 怎么选

比较可用入口、部署要求、状态复杂度、性能、维护预算、版本变化、验证覆盖、恢复成本。

一个常见误判：以为「底层算法稳定 → T1 低维护」。算法确实稳定，但**认证、风控、会话、设备指纹经常变**，这部分才是 T1 的主要维护成本。反过来，内部函数名/签名/对象布局/ABI 的变化频率**必须按版本实测**，不能预设「几乎零维护」——两者都要用真实回归工时比较，而不是用直觉。

T2 的适用场景要写进契约：需要大规模并发、无桌面部署、交付给第三方时，T1 的优势才真正压过维护成本。

## 信息卫生

研究记录只保留泛化占位符：`APP`、`APP_VERSION`、`FEATURE`、`OBJECT_ID`、`ENDPOINT`、`AUTH_CONTEXT`。原始数据留在受控研究区，证据引用用相对路径；凭据由调用方运行时提供，不写入模板、日志、异常或仓库。
