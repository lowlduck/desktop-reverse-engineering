# 桌面端 AI 逆向开发指南

> **把桌面应用的一个功能，做成稳定、可复用、可编程的接口。**
> 本文**不绑定任何产品**：正文只写动作、判断与纪律。所有结论的出处抽象成两类客户端形态，
> 具体是哪些产品见[附录 D](#附录-d证据出处脱敏可选)。

## 两类客户端形态（本文的证据来源，也是选型轴）

| 形态 | 特征 | 典型交付等级 | 覆盖章节 |
|---|---|---|---|
| **形态 A**<br>前端型 | CEF/Electron 壳 + 前端 bundle；业务走 HTTP/JSON 与 WebSocket | 可达 **T1**（协议自主实现） | 1–13 |
| **形态 B**<br>原生单体型 | 单个大 exe、无前端资源；自研编码器 + 单端点隧道 + 多层加密 | **T2**（自造载荷 + 复用客户端发送管道） | 14–16 |

> 具体产品名、版本号、字段值只在**证据**位置出现，写成「案例 A（前端型，VER 5.x）」这样。
> 判断一个新目标属于哪种形态 → [附录 C](#附录-c两类形态对照选型用)。
>
> **贯穿示例**：形态 A 用「发一条消息」，形态 B 用「创建一个服务端对象（建群）」作例子。
> 都是**示例功能**，换成"发文件""改资料""下单"同样适用。

> **目标形态**：从 0 基础 0 经验，在只知道「要逆向某个功能，纯协议完成，禁止 UI 自动化」的前提下，
> 走到能**稳定、可高复用**的功能调用接口。
>
> ⚠️ **「接口」不等于「HTTP 接口」**。绝大多数桌面应用的底层协议并不只有 HTTP：
>
> | 协议类型 | 典型场景 | 抓法 |
> |---------|---------|------|
> | **HTTP / HTTPS** | 业务接口、文件上传、消息发送 | 网络层 hook / 日志 hook / CDP |
> | **WebSocket** | 长连接、消息推送、心跳、实时同步 | hook 帧发送函数 / CDP WS 帧 |
> | **TCP 自定义协议** | IM 消息、登录握手、私有 RPC | hook `send`/`SSL_write` + 还原帧结构 |
> | **UDP** | 音视频流、发现协议、游戏同步 | hook `sendto`/`recvfrom` |
> | **共享内存 / 命名管道 / RPC** | 主进程 ↔ 子进程、本地服务 | hook 对应 API（`CreateFileMapping` 等） |
> | **SQLite / 本地文件** | 离线数据、缓存、待发队列 | 直接读库 / hook 写文件 |
>
> 案例 A（前端型）恰好走 HTTP（`API_ENDPOINT`），同一次研究里也遇到 WebSocket（`WS_SEND_FN`）；
> 案例 B（原生型）则完全不是 HTTP 语义——一个端点、双层加密、命令类型埋在载荷里。
> **判断「这个功能走哪条通道」本身就是逆向的第一步**（见第 3 章）。
>
> **真正要交付的是这三件事**：
> 1. **稳定** —— 能长期跑，不因登录态刷新/连接断开就崩
> 2. **高复用** —— 换个参数（换用户、换目标、换内容）依然能用，不是硬编码重放
> 3. **可编程** —— 别人拿到就能调，不依赖 UI、不依赖人工点击
>
> **关于「要不要关掉客户端」**：
> - **关掉也能跑 = 最优（T1）** —— 案例 A 做到了（凭据除外）
> - **客户端在跑、但走接口调用 = 也合格（T2）** —— 只要不点 UI，就算功能调用接口；案例 B 是这种
>
> 详见 [1.6 达标标准](#16-达标标准两级)。**别因为做不到脱机就以为没做成。**
>
> **性质**：经验总结 + 决策树 + 工具矩阵 + 避坑清单。协议无关，HTTP 只是其中最常见的一种。

## 🔖 可信度标记体系（重要，先读）

> 本文档的每条结论都带标记。**只有 ✅ 才能直接照抄使用**，其余需要用你自己的环境验证。

| 本文标记 | 等价说法（研究记录里常用） |
|:---:|---|
| ✅ | VALIDATED / OBSERVED —— 真实执行过，有命令、日志或输出可查 |
| 🟡 | PARTIAL —— 走通过但有明确限制或副作用 |
| 💭 | HYPOTHESIS —— 有证据支撑的推理，未执行 |
| ❓ | UNTESTED —— 纯假设，只作思路参考 |

> 标记要跟**版本**和**证据路径**一起写，否则半年后无法判断是否还成立。

| 标记 | 含义 | 判断依据 | 使用建议 |
|:----:|------|---------|---------|
| ✅ | **实战验证** | 本次研究中**真实执行过**，有命令/日志/输出/结果可查 | 可直接复用，仍需注意版本差异 |
| 🟡 | **部分验证** | 执行过但**未完整走通**，或有明显副作用/限制 | 可以参考，但要预留调试时间 |
| 💭 | **推理待验证** | 基于已有证据**推断**，逻辑成立但**没实际执行** | 当作假设，先小成本试一次 |
| ❓ | **未验证** | 经验性假设，**没有任何证据支撑** | 只作思路参考，不要当结论 |

# 0. 先读这个：一页决策树

## 0.0 第一件事：定目标层级

```
产品只要"能用"？
├─ 是 → 优先 T2b（CDP，最快）或 T2a（注入 DLL）
└─ 否（要批量/脱机）→ 目标定在 T1（纯协议）
        ↓
     T1 逆不出来怎么办？
     ├─ 有壳/加密 → 先判断壳类型（别急着退回！）
     │    ├─ 压缩壳/加密壳  → ✅ 值得脱（分钟~小时）
     │    ├─ 虚拟化壳(VMProtect) → 不脱壳，先试「边界 hook / 调而不破」
     │    │      └─ 都失败 → 才退回 T2a
     │    └─ 硬件绑定 → 直接退回 T2a/T2b
     └─ CEF 架构 → 退回 T2b

详细分层见第 1 章；壳的处理见 8.1（含决策树）。
```

> ⚠️ **不要一遇到壳就降级** —— 先分清壳的类型。
> 虚拟化壳确实难破，但**大多数时候根本不需要破**：从边界观察行为（日志/网络/内存）成本低 100 倍。
> 详见 [8.1 壳——先分类，再决定破不破](#81-壳packers-先分类再决定破不破)。

## 0.1 技术路线决策树

```
拿到目标：「逆向 XXX 功能的接口，纯协议，禁 UI 自动化」
│
├─ 第 0 步：花 30 分钟做侦察（见第 2 章），回答 5 个问题：
│   ① 是 CEF / Electron / 纯原生？
│   ② 有没有壳（VMProtect/Themida）？
│   ③ 有没有数字签名校验 / 完整性校验？
│   ④ 日志是明文还是加密？
│   ⑤ 有没有本地数据库（可解密？）
│
├─ 分支 A：应用会写【明文日志】
│   └─ ★★★★★ 最优路线：hook 日志函数（内存 patch）
│       → 一次拿到全部请求 URL + Body
│       → 本次研究就是靠这个一击致命
│
├─ 分支 B：【CEF / Electron】且能开 DevTools
│   └─ ★★★★ 路线：CDP + 页面内部函数
│       → 能直接调用页面自己的发送函数（复用其签名/加密）
│       → 需要先解决「怎么开 DevTools」（启动器替换法）
│
├─ 分支 C：纯原生 + 有自己的 HTTP 层 DLL
│   └─ ★★★★ 路线：DLL 代理 + vtable patch
│       → 能抓 URL + Body + Headers
│       → 注意虚函数、线程安全、导出名
│
├─ 分支 D：有本地数据库（SQLite / SQLCipher）
│   └─ ★★★ 路线：直接读库
│       → 能找到历史消息、会话 ID、用户 ID
│       → 密钥通常在二进制里（搜字符串 / hook 打开函数）
│
├─ 分支 E：以上都不行
│   └─ ★★ 路线：内存扫描 + 行为对比
│       → 能拿凭据、消息结构
│       → 缺点：触发刷新、时序敏感
│
└─ ❌ 永远不要先试（浪费时间的备选方案）：
    · 系统代理 / mitmproxy（CEF 系全部忽略）
    · Frida / x64dbg（有壳就 100% 被拦）
    · 替换被签名校验的 DLL（必崩）
    · IFEO 注入同 exe 参数（无限递归，进程爆炸）
```

**⚠️ 最重要的一条经验：**
> **先找「日志」，再找「网络」。**
> 90% 的桌面应用会把请求参数写进日志（用于排障），
> 而日志通常**没有反调试保护**——它是整条链路上最软的柿子。

# 1. 目标拆解：分层目标模型

> **核心认知：一开始就要分清「产品目标」和「技术目标」，
> 并且给技术实现排一个优先级阶梯——否则容易在"能跑就行"里躺平，或者在不该硬刚的地方耗尽预算。**

---

## 1.1 两种目标，别混为一谈

| 视角 | 关心什么 | 判定标准 | 举例（案例 A：发视频） |
|------|---------|---------|------------------------------|
| **产品 / 业务** | 功能**能不能用** | 那一条视频真的发出去了 | 视频出现在买家的聊天窗口 |
| **技术 / 工程** | 实现方式**可不可持续** | 不依赖客户端、可批量、可复现 | 关掉工作台，一条 `curl` 也能发 |

**这两件事经常被混着说："我就要能发视频"——但"能发"有 5 种做法，成本差 10 倍。**

> ⚠️ 实战建议：**开工前先跟需求方对齐一句话——**
> 「你是要**这一次能用**，还是要**以后随时能批量用**？」
> 答案不同，走的路线完全不同。

---

## 1.2 目标阶梯（按优先级排序）

> **原则：优先选高层级（T1），但允许按现实降级。**
> 每个层级都算"交付"，只是成本和可持续性不同。

```
        优先级高 ↑                                   成本低 ↓
   ┌──────────────────────────────────────────────────────────┐
   │  T1  纯协议（无客户端）          最优 ★★★★★  但慢/难      │
   ├──────────────────────────────────────────────────────────┤
   │  T2a 注入自研 DLL 调客户端函数    ★★★★     需客户端运行   │
   │  T2b CDP 调页面内部函数           ★★★      需 DevTools   │
   ├──────────────────────────────────────────────────────────┤
   │  T0  人工操作打通一次（基准）     ✓ 必须先有              │
   ├──────────────────────────────────────────────────────────┤
   │  T3  UI 自动化                    ✗ 不合格               │
   └──────────────────────────────────────────────────────────┘
```

### 总览表

> ⚠️ **「优先级」这一列指的是「能力上限」，不等于「性价比」。**
> 实际项目里 **T2a 往往更划算** —— 理由见 [1.6.2](#162-反直觉的现实实际项目里-t2a调函数用得更多)。
> T1 是"能飞"，T2a 是"够用且省油"。**先飞起来，再考虑要不要上天。**

| 层级 | 实现方式 | 前置条件 | 产物形态 | 周期 | 难度 | 可否批量 | 能力上限 |
|------|---------|---------|---------|------|------|---------|--------|
| **T1** | 纯协议复现（HTTP / WS / TCP / UDP 等） | **无**（只要凭据） | 脚本/服务，可部署到任何机器 | **长**（小时→天） | **高** | ✅ 高并发 | **★★★★★ 最高** |
| **T2a** | 注入自研 DLL，调客户端导出/内部函数 | 客户端**运行中** + 已登录 | DLL + 注入器 + 调用封装 | 中 | 中 | ⚠️ 受限于客户端实例 | ★★★★ |
| **T2b** | CDP 调页面内部 JS 函数 | 客户端**运行中** + DevTools 可开 | Python CDP 脚本 | **短** | 低 | ⚠️ 同上 | ★★★ |
| **T0** | 人工点一遍 | 有账号 | 一段屏幕录像/截图 | 分钟 | 极低 | ✗ | 必须先做（基准） |
| **T3** | UI 自动化（pyautogui/RPA） | 客户端运行 + 有窗口 | 点击脚本 | 短 | 低 | ⚠️ 极脆弱 | ✗ **不合格** |

### 维护成本对比（比"能力上限"更影响实际选择）

| 层级 | 你要自己维护什么 | 变化风险 |
|------|-----------------|---------|
| **T1** | 协议 + 字段 + 签名算法 + 登录/风控/设备指纹 | **高**（认证风控经常变） |
| **T2a** | 函数签名 / 导出名 | **低**（很少变） |
| **T2b** | 页面函数名 | 低-中（页面改版会变） |
| **T3** | 坐标 / 控件树 / 截图 | **极高**（改版就废） |

## 1.3 各级详解

### T1 —— 纯协议（**最优目标**）

**定义**：不运行客户端，**用该功能实际使用的协议**直接复现。
协议可能是 HTTP / HTTPS / WebSocket / 自定义 TCP / UDP / 本地 RPC ——
**先判断走哪条通道，再谈复现**（见第 3 章）。

**典型产物（HTTP 版，本次案例）：**
```python
# 关掉工作台，这条也能跑
requests.post(
    "https://API_HOST/path/to/endpoint",
    headers={"Cookie": f"LOGIN_TOKEN={pass_id}", "Content-Type": "application/json"},
    json={"uid": "UID_SAMPLE", "url": "https://CDN_HOST/.../xxx.mp4"},
)
# → {"success": true, "error_code": 1000000}
```

**典型产物（自定义 TCP 版，形态示意）：**
```python
# 长连接 + 自定义帧：长度头 + 命令字 + JSON/Protobuf + 校验
s = socket.create_connection(("host", 8080))
s.sendall(frame(cmd=0x1001, payload=json.dumps({...}), sign=sign_of(...)))
resp = read_frame(s)          # 自己拆帧
```

**典型产物（WebSocket 版）：**
```python
ws = websocket.create_connection("wss://host/path", header=[f"Cookie: {ck}"])
ws.send(json.dumps({"cmd": "send_message", "message": {...}, "random": sign}))
resp = json.loads(ws.recv())
```

> 💡 **判据不是「是不是 HTTP」，而是「关掉客户端还能不能发出去」。**
> 只要协议、凭据、签名都能自己产出，**TCP/UDP 一样算 T1 达标**。

**优点：**
| 优点 | 说明 |
|------|------|
| 可部署 | 能跑在服务器 / 容器 / 云函数 |
| 可批量 | 无实例上限，高并发 |
| 抗版本 | 接口比客户端稳定（客户端改版常不动协议） |
| 可交付 | 别人拿到脚本就能用，不需要装客户端 |
| 可监控 | 能加日志、重试、限流 |

**代价：**
- 要逆出**完整参数 + 签名算法 + 认证链路**
- 遇到强壳 / 加密 / 风控会卡很久
- **研究周期最长**

> **为什么仍然优先？**
> 因为它是**唯一能规模化**的产物。T2 的所有方案都受制于「客户端必须开着」，
> 一旦要跑 100 个账号，T2 全部崩盘。

---

### T2a —— 注入自研 DLL，调客户端函数（**快而合格**）

**定义**：自己写一个 DLL，注入到客户端进程里，直接调用客户端内部的导出函数 / 内部函数。

```
┌─────────────────────────────────────────┐
│ 客户端进程（TARGET.exe）            │
│  ┌───────────────────────────────────┐  │
│  │ 我们注入的 my_bridge.dll           │  │
│  │   ↓ 直接调用                       │  │
│  │ CMChatImpl::SendFileCardToService │  │
│  │   ↓                                │  │
│  │ 客户端自己的网络栈 + 签名 + 登录态   │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

**关键特征：**
| 项 | 说明 |
|---|------|
| 前置条件 | 客户端**必须正在运行且已登录** |
| 需自研 | ✅ 要写 DLL（注入器 + 调用封装 + IPC 返回结果） |
| 是否算"无自动化" | ✅ **算**——不是点 UI，是调函数 |
| 周期 | 中（比 T1 短，因为不用逆签名/加密） |
| 稳定性 | 客户端改版可能改函数签名 → 需跟随 |

**适用场景：**
- 协议里有**无法逆的算法**（强壳 + 自研加密）
- 时间紧，只要**先打通**
- 客户端本来就要长期开着（例如客服工作台）
- **生产环境更稳**：签名/加密由客户端自己算，协议改版也不受影响

> ✅ **T2a 是合格交付**，不是"过渡产物"。只要不点 UI，它就是「功能调用接口」。
> 它唯一的硬伤是**客户端必须开着**（可部署性、并发量受限），这是成本问题，不是合格性问题。

**实现要点：**
```cpp
// 1. 注入后拿到目标函数地址
HMODULE h = GetModuleHandleA("MsgSDK.dll");
auto fn = (SendFileCard_t)GetProcAddress(h,
    "?SendFileCardToService@CMChatImpl@@QEAA_NAEBV...");

// 2. 直接调用（复用客户端的登录态、签名、网络栈）
std::string result;
bool ok = fn(thisPtr, session_id, receiver_id, file_path, file_id, size, result);

// 3. 把结果通过命名管道/共享内存返回给外部控制程序
```

> ⚠️ 本次未能实现 T2a（VMProtect 让取 `this` 指针和函数签名变得困难），
> 但这是**技术上完全可行**的路线，只是需要更多逆向工作。

### T2b —— CDP 调页面内部函数（**最省事的合格方案**）

**定义**：客户端是 CEF/Electron 时，开 DevTools，直接 `Runtime.evaluate` 调页面暴露的内部函数。

```javascript
// 直接调页面自己的发送函数，签名/加密/登录态全部复用
socketUtil.sendMsg({
  uid: "UID_SAMPLE",
  csid: "cs_753894465_190840895",
  content: "你好",
  type: 0
})
```

**关键特征：**
| 项 | 说明 |
|---|------|
| 前置条件 | 客户端运行 + **DevTools 能开** |
| 需自研 | ❌ 不用写 DLL，只写 Python CDP 脚本 |
| 是否算"无自动化" | ✅ 算——不是点 UI，是执行函数 |
| 周期 | **最短**（本次 1 小时打通文本发送） |
| 稳定性 | 页面改版可能改函数名 |

**适用场景：**
- 客户端是 CEF/Electron
- **直接作为交付**（客户端本来就长期开着，比如客服工作台）
- 只需要**验证协议理解** / 做侦察探针
- 快速验证「这个功能到底怎么发的」

> ✅ **T2b 本身就是合格交付**（不是"过渡产物"）—— 它不是 UI 自动化，是调函数。
> 只要客户端在跑、参数能换、跑得稳，就满足 1.6 的「基础达标」。
>
> 💡 **本次还把 T2b 当"探针"用**：
> 先用 CDP 调 `socketUtil.sendMsg` 发文本成功 → 证明「消息通道理解了」；
> 视频失败 → 说明视频走的不是这条路 → 逼着我们继续找 T1 的路径。
> **T2b 既能交付，也是极好的侦察工具。**

### T0 —— 人工打通一次（必须先做）

**作用**：建立**基准事实**。

```
□ 人工点一遍，确认功能真的存在
□ 录屏 / 截图留证
□ 记录：发给谁、发了什么、界面反馈是什么
```

**为什么必须先做：**
- 后面所有自动化都要和这一次对比
- 万一功能本身有问题（权限/风控/账号），先排除
- 给"成功"下一个明确定义

---

### T3 —— UI 自动化（**不合格**）

**为什么不合格：**
| 问题 | 说明 |
|------|------|
| 极脆弱 | 分辨率/主题/语言/更新 都会挂 |
| 无法批量 | 每台机器要一个真实桌面 |
| 无法监控 | 出了错只能看截图 |
| 不可交付 | 别人拿到脚本跑不起来 |
| **本次明确禁止** | 需求方硬约束 |

> 只有一种情况可以考虑：**T1/T2 全部失败，且只需要一次性过渡**。
> 即便如此，也要明确标注为"临时方案"，不能作为交付物。

## 1.4 决策：什么时候降级到 T2

```
开始
 │
 ├─ 有时间预算（≥1 天）？
 │   └─ 有 → 死磕 T1（纯协议）
 │
 ├─ 有强壳 + 自研加密 + 无法逆？
 │   └─ 是 → 评估 T2a（注入 DLL）
 │
 ├─ 客户端是 CEF/Electron？
 │   └─ 是 → 先上 T2b（CDP）快速侦察，再决定要不要回头做 T1
 │
 └─ 时间紧（<1 天）且只要打通？
     └─ T2b（有 CEF）或 T2a（原生）
```

**降级的三个正当理由：**
1. 算法确实逆不出（强壳 + 硬件绑定）
2. 时间预算不允许
3. 客户端本来就长期开着（业务形态匹配）

**降级的代价（要提前告知需求方）：**
- 无法部署到无客户端的机器
- 无法大规模并发
- 客户端更新可能要跟着改

## 1.6 达标标准（两级）

> ⚠️ **先纠正一个常见误解：能脱机不是硬门槛。**
>
> | | 关掉客户端也能发 | 客户端在跑，但走接口调用 |
> |---|---|---|
> | 等级 | **最优（T1）** | **可接受（T2）** |
> | 评价 | 最好 | 也是合格交付，不是"半成品" |
> | 只要不点 UI，都算「功能调用接口」 | ✅ | ✅ |
>
> **T2 的唯一硬伤是「客户端必须开着」**，代价是可部署性、并发量、稳定性受限于客户端——
> 但这些是**成本问题，不是合格与否的问题**。预算够就冲 T1，预算紧就交 T2，都能用。

---

### 基础达标（T2 即可，**合格交付**）

满足下面全部，就算交付了一个**可编程的功能调用接口**：

| # | 标准 | 验证方式 |
|---|------|---------|
| 1 | **不依赖 UI 自动化** | 没有任何坐标点击/截图识别/键鼠模拟 |
| 2 | 知道**调的是哪个函数或哪个端点** | 能说出具体函数名 / URL / 命令字 |
| 3 | 知道**完整入参**（名称 + 类型 + 取值范围） | 能自己构造出被接受的数据 |
| 4 | 能**换参数** | 换 uid / 换内容 / 换目标 → 仍然成功 |
| 5 | **稳定**（见 1.6.1） | 凭据过期、断连都能自动恢复 |
| 6 | **契约清晰** | 入参/出参/错误码有明确语义，别人看文档就能调 |

> 💡 **T2 的典型形态**：
> - **T2a** —— 注入自研 DLL，直接调客户端导出函数
> - **T2b** —— CDP 调页面内部 JS 函数（`socketUtil.sendMsg` 这种）
>
> 这两种都**不是 UI 自动化**，都算合格。

---

### 最优达标（T1，**关掉客户端也能跑**）

在基础达标之上，再加这两条：

| # | 标准 | 验证方式 |
|---|------|---------|
| 7 | 知道**确切的协议与寻址**<br>HTTP → `URL / 方法 / Content-Type`<br>WS → `wss URL / 子协议`<br>TCP/UDP → `host:port / 帧格式 / 命令字` | 抓包、日志或 hook 能看到 |
| 8 | 知道**签名/加密/序列化算法**，或能直接复用（不绑定 payload） | 能自己算，或能安全复用 |

> ✅ 满足这两条，就能脱离客户端独立复现 —— 这才是"最优"。
> 满足不了也不影响交付，只是意味着**必须让客户端活着**。

---

### 怎么选

```
预算充足 且 协议不太难逆  → 冲 T1（脱机，最优）
预算紧   或 强壳/强加密    → 交 T2（客户端在跑，合格）
```

> **不要因为"做不到脱机"就认为没做成。**
> 很多生产环境里，T2a（注入 DLL 调函数）反而是更稳的选择 —— 因为签名/加密都由客户端自己算，你永远不会因为协议改版而失效。

## 1.6.1 什么叫「稳定、高复用」（交付前的自检）

> 这三个词经常被说得很虚，这里给出可检验的标准。

### 稳定（Stable）

| 检查项 | 通过标准 |
|--------|---------|
| 凭据过期 | 能**自动重新获取**，不需要人工登录 |
| 连接断开 | 能自动重连 / 重试，有退避 |
| 客户端改版 | 协议层不受影响（或改动范围可预期） |
| 异常返回 | 有明确错误码映射，不是"挂了不知道为啥" |
| 长时间运行 | 跑 24 小时不崩、不泄漏连接 |

### 高复用（Reusable）

| 检查项 | 通过标准 |
|--------|---------|
| 换身份 | 换账号/uid 能直接用（凭据是参数，不是硬编码） |
| 换目标 | 换接收方/会话/文件能直接用 |
| 换内容 | 换文本/图片/视频能直接用（类型驱动，不是写死） |
| 并发 | 多实例同时跑不互相干扰 |
| 无状态 | 不依赖"上一次调用的残留状态" |

### 可编程（Programmable）

| 检查项 | 通过标准 |
|--------|---------|
| 无需 UI 自动化 | 没有坐标点击 / 截图识别 / 键鼠模拟 |
| 无需人工 | 全流程自动，无点击 / 无扫码 / 无手工填参 |
| 可嵌入 | 能作为函数/服务被别的程序调用 |
| 可观测 | 有日志、有返回码，失败能定位 |
| 无需客户端 ✨ | **加分项**：关掉客户端也能跑（T1） |

> ✅ **前四条满足 = 合格的「功能调用接口」（T2 即可）；第五条满足 = 最优（T1）。**
> 只满足「能跑一次、换个参数就废」= 还没有交付。

## 1.6.2 反直觉的现实：**实际项目里 T2a（调函数）用得更多**

> 这一节是对「T1 是唯一正确答案」这个直觉的修正。

### 关键观察：**底层算法很少变，但认证/风控经常变**

很多人以为 T1（纯协议）最大风险是"算法会变"。**实际上算法恰恰是最稳定的部分。**

| 变动频率 | 变动对象 | 对 T1 的影响 | 对 T2a 的影响 |
|:--------:|---------|-------------|--------------|
| **几乎不变** | 签名算法 / 加密算法 / 序列化格式 | 一次逆出来就长期有效 | 无影响（客户端自己算） |
| **偶尔变** | 业务接口 URL / 字段名 / 参数结构 | ⚠️ **要跟着改** | 无影响（调函数，不碰 URL） |
| **经常变** | 登录流程 / 风控 / 设备指纹 / 验证码 | ⚠️⚠️ **要跟着改，而且最难** | 无影响（客户端自己维护） |
| **偶尔变** | 函数签名 / 导出名 / 调用约定 | 无影响 | ⚠️ 要跟着改（但通常很快） |

### 结论

```
T1 的维护负担 = 算法（稳定） + 接口（易变） + 认证风控（很易变）
T2a 的维护负担 = 函数签名（偶尔变）

→ T2a 把「最易变的部分」外包给了客户端
→ 所以实际项目里 T2a 用得更多、活得更久
```

### 什么时候 T1 仍然值得

| 场景 | 原因 |
|------|------|
| 要**大规模并发**（几十上百账号） | T2a 一台机器开不了那么多客户端 |
| 要**部署到无桌面环境**（Linux 服务器/容器） | T2a 必须跑在 Windows 桌面 |
| 要**给别人用**（不装客户端） | T2a 交付不了 |
| 客户端**本来就不该长期开着** | 业务形态不匹配 |

**除此之外，T2a 往往是更务实的选择。**

### 一句话

> **算法稳定 → T1 的"技术难度"没想象中高；
> 但认证风控易变 → T1 的"维护成本"比想象中高。
> T2a 用「客户端必须开着」换「几乎零维护」，这笔交易大多数时候是划算的。**

## 1.7 明确「不算完成」的情况

| 情况 | 属于 | 为什么不达标 |
|------|------|-------------|
| 情况 | 属于 | 为什么不达标 |
|------|------|-------------|
| 用 `pyautogui` / `pywinauto` 点按钮 | T3 | **UI 自动化，禁** |
| 用 RPA 抓屏幕 / 图像识别找按钮 | T3 | 同上 |
| 只能通过「重放完整抓包」（含一次性 nonce） | 伪达标 | 不能换参数，不能批量 |
| **调用客户端内部函数（需客户端在跑）** | **T2** | ✅ **这是合格交付**，不是"半成品" —— 只要不点 UI 就算 |
| 只跑通一次，换个 uid 就失败 | 未达标 | 说明还有硬编码/绑定的东西没逆出来 |
| 凭据过期就要人工重新登录 | 不够稳定 | 没做到「稳定」，见 1.6.1 |
| 只支持一种消息类型（写死了文本/视频） | 不够复用 | 没做到「高复用」，见 1.6.1 |
| 需要用户手动打开某个页面/勾选某项才能跑 | 不算自动化 | 还是人工介入 |

## 1.8 一句话总结

> **产品要的是「打通」，技术要的是「稳定 + 可复用」。**
>
> - **T3（UI 自动化）永远不算交付**
> - **T2（客户端在跑，走接口调用）= 合格交付**
> - **T1（关掉客户端也能跑）= 能力上限最高，但不强求**
>
> **协议是 HTTP 还是 TCP/UDP 不重要，客户端开着还是关着也不是决定性的 ——**
> **能换参数、能长期跑、别人拿到就能调，才叫「功能调用接口」。**
>
> ---
>
> **而在真实项目里，T2a（注入 DLL 调函数）往往才是最优解**：
>
> ```
> 底层算法很少变  →  T1 的技术门槛没那么高
> 但认证风控常变  →  T1 的维护成本比想象中高
> 函数签名很少变  →  T2a 几乎零维护
> ```
>
> **T2a 用「客户端必须开着」换「几乎不用维护」—— 这笔交易大多数时候是划算的。**
> 只有当你要**大规模并发 / 无桌面部署 / 交付给别人**时，T1 的优势才真正压过维护成本。

# 2. 第 0 阶段：30 分钟侦察（决定成败）

> **这一阶段不做任何 hook、不写任何代码。**

## 2.2 模块依赖分析（判断网络层）

```python
import pefile, glob, os

for f in glob.glob(r"<安装目录>\*.dll") + glob.glob(r"<安装目录>\*.exe"):
    pe = pefile.PE(f, fast_load=True)
    pe.parse_data_directories(directories=[
        pefile.DIRECTORY_ENTRY['IMAGE_DIRECTORY_ENTRY_IMPORT']])
    for e in getattr(pe, 'DIRECTORY_ENTRY_IMPORT', []):
        dll = e.dll.decode(errors='ignore').lower()
        if any(k in dll for k in ['curl', 'winhttp', 'wininet', 'ws2_32',
                                  'ssl', 'crypt', 'request', 'network']):
            print(f"{os.path.basename(f):40} → {dll}")
```

**看什么：**
| 导入的 DLL | 含义 | 对应 hook 点 |
|-----------|------|-------------|
| `libcurl.dll` | 用 libcurl 发 HTTP | `curl_easy_setopt` / `curl_multi_*` |
| `PDDRequest.dll` / `xxxRequest.dll` | **自研 HTTP 层** | 该 DLL 的导出/虚函数 |
| `WS2_32.dll`（除 WSAStartup） | 裸 socket | TLS 层之上抓不到明文 |
| `LIBEAY32` / `SSLEAY32` | OpenSSL | 可 hook `SSL_write` 拿明文 |
| `winhttp.dll` / `wininet.dll` | 系统 HTTP | 可 hook 系统 API |

> ⚠️ **本次教训**：只看到 `WS2_32.WSAStartup`（仅初始化）时，别以为它不用网络——
> 真正的 HTTP 是 `PDDRequest.dll` 转发的，而 `PDDRequest.dll` 又 import 了 `libcurl.dll`。
> **要递归看依赖链**。

# 3. 核心心智模型：桌面端的三层两通道

> 理解了这张图，你就知道该往哪儿下钩子。

```
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层：UI / 前端                                            │
│   · CEF 页面（Chromium）或 原生 DuiLib/Qt                    │
│   · JS 通过【原生桥】调用下层                                  │
│   钩子点：CDP 注入 / 本地 JS 静态分析                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ 原生桥（pinbridge / cefQuery / window.chrome）
┌───────────────────────────▼─────────────────────────────────┐
│ 第 2 层：业务 SDK                                             │
│   · MsgSDK.dll / AccountBusiness.dll …                       │
│   · 构造业务 JSON、算签名                                     │
│   钩子点：DLL 代理 + vtable patch / 导出 hook                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 内部 API 调用
┌───────────────────────────▼─────────────────────────────────┐
│ 第 1 层：网络层                                               │
│   · libcurl / winhttp / 自研网络库(AntInterface.dll)         │
│   钩子点：libcurl hook / vtable patch                        │
└───────────────────────────┬─────────────────────────────────┘
                            │
                    ════════╧════════  网络
                    
另外两条「旁路通道」（往往比主路更好用）：
  A. 日志通道：任何一层的日志函数 → 明文请求参数  ★★★★★
  B. 数据通道：本地数据库 / 缓存 / 内存字符串      ★★★
```

## 3.1 两个通道（消息类应用特有）

```
请求-响应通道（HTTP）
  → 适合：发消息、查列表、上传
  → 抓法：网络层 hook / 日志 hook

长连接通道（WebSocket / 自定义 socket）
  → 适合：收消息、推送、心跳
  → 抓法：hook socket 发送函数 / hook 消息分发函数
  → 本次发现：WS_SEND_FN（原生桥暴露给 JS）
```

> **本次关键判断**：文本消息走 socket，视频卡片走 HTTP。
> 一开始误以为都是 socket，浪费了一轮实验。
> **教训：先确定「这个功能走哪条通道」，再选工具。**

## 3.2 怎么快速判断走哪条通道

| 现象 | 结论 |
|------|------|
| 抓包看到完整 HTTP 请求 | 走 HTTP |
| 只有一个长连接，且数据是二进制帧 | 走 WebSocket / 自定义 socket |
| 请求参数在内存里能搜到 JSON | 可能走 socket 或本地构造后 HTTP |
| 日志里有 `request parameter, <url>, <body>` | 一定走 HTTP |

**CDP 能做什么（本次实测）：**
| 能力 | CDP 命令 | 价值 |
|------|---------|------|
| 抓所有请求 | `Network.requestWillBeSent` | 含 URL/headers/body |

| 执行页面 JS | `Runtime.evaluate` | **直接调内部函数**（最强） |

| 读页面全局 | `Runtime.evaluate("Object.keys(window)")` | 找 `socketUtil` 这类宝库 |

> 💡 **本次最高价值的一步**：
> `Object.keys(window)` 发现 `window.socketUtil.sendMsg`，
> 直接调用它发文本消息成功——**省掉整个协议还原过程**。

## 4.2 纯原生

```
有自研 HTTP DLL（名字含 Request/Network/Http）？
├─ 有
│   ├─ 函数是【导出】的 → 直接 DLL 代理 + 转发 + hook

└─ 没有
```

## 5.6 自写 MCP 客户端（重要技巧）

> **问题**：MCP 是 stdio 协议，AI 无法直接调；且进程一退出浏览器就关了。

**解法：命令文件驱动的常驻守护**

```python
# mcp_daemon.py 核心逻辑
proc = subprocess.Popen(["node", MCP_JS] + args,
                        stdin=PIPE, stdout=PIPE, text=True, bufsize=1)

def send(method, params, notify=False):     # JSON-RPC 2.0，行分隔
    msg = {"jsonrpc": "2.0", "method": method, "params": params}
    if not notify:
        msg["id"] = next_id()
    proc.stdin.write(json.dumps(msg) + "\n"); proc.stdin.flush()

# 主循环：监听 mcp_cmd.json → 执行 → 写 mcp_result.json
while True:
    if os.path.exists(CMD):
        req = json.load(open(CMD, encoding="utf-8-sig"))   # 容忍 BOM
        res = call_tool(req["tool"], req["args"])
        json.dump({"ok": True, "result": res}, open(RES, "w"))
```

**踩坑：**
- PowerShell 写 JSON 会带 **BOM** → Python 读取要 `encoding="utf-8-sig"`
- PowerShell 会**吞掉参数里的引号** → 改用 `@args.json` 文件传参
- MCP 进程退出会带走浏览器 → 必须常驻

# 6. 王牌技术：日志侧信道

> **本次一击致命的技术。值得单独一章。**

## 6.1 为什么日志是金矿

| 优势 | 说明 |
|------|------|
| **无保护** | 日志函数通常不做反调试、不校验调用者 |
| **信息全** | 请求 URL + Body + 响应 + 错误码，全都有 |
| **明文** | 加密的是**落盘文件**，函数入参是明文 |
| **一次到位** | 不用逐个接口抓 |

## 6.2 三步走

### Step 1：找到日志函数

**典型结果：**
```

?LogFormat@CLog@@SAXW4LogPriority@@PEBDH11ZZ   ← 带级别
```

**怎么解读 mangled name：**
```
?LogFormat@CLog@@SAX W4LogPriority@@ PEBD H 1 1 Z Z
                        │    │             │    │ │ │ │ └─ varargs
                        │    │             │    │ │ │ └─── const char* (fmt)
                        │    │             │    │ │ └───── const char* (func)
                        │    │             │    │ └─────── int (line)
                        │    │             │    └───────── const char* (file)
                        │    │             └────────────── 枚举 LogPriority
                        │    └──────────────────────────── __cdecl
                        └───────────────────────────────── static
```

### Step 2：决定 hook 方式

```
能替换 DLL 且无签名校验？
├─ 能 → DLL 代理（转发所有 + hook 日志函数）
└─ 不能 → 内存内联 patch（见下）
```

**内存内联 patch 模板（关键代码）：**

```cpp
// 1. 后台线程等 DLL 加载
DWORD WINAPI PatchThread(LPVOID) {
    for (int i = 0; i < 600; i++) {          // 最多等 60 秒
        HMODULE mod = GetModuleHandleA("PDDLog.dll");
        if (mod) {
            void* f = GetProcAddress(mod,
                "?LogFormat@CLog@@SAXW4LogPriority@@PEBDH11ZZ");
            if (f) InstallJmp(f, (void*)hook_LogFormat);
            return 0;
        }
        Sleep(100);
    }
    return 0;
}

// 2. 写 jmp（14 字节 = FF 25 00000000 + 8 字节目标）
void InstallJmp(void* target, void* hookFn) {
    BYTE patch[14] = {0xFF, 0x25, 0, 0, 0, 0};
    *(void**)(patch + 6) = hookFn;
    DWORD old;
    VirtualProtect(target, 14, PAGE_EXECUTE_READWRITE, &old);
    memcpy(target, patch, 14);
    VirtualProtect(target, 14, old, &old);
    FlushInstructionCache(GetCurrentProcess(), target, 14);
}

// 3. varargs hook —— 用 vsnprintf 格式化，不调原函数
extern "C" void __cdecl hook_LogFormat(
        int pri, const char* file, int line,
        const char* func, const char* fmt, ...) {
    char buf[8192];
    va_list ap; va_start(ap, fmt);
    _vsnprintf_s(buf, sizeof(buf), _TRUNCATE, fmt, ap);
    va_end(ap);
    WriteToFile(buf);       // ★ 不调用原函数 → 避免 trampoline
}
```

**为什么「不调用原函数」是安全的：**
- 日志函数返回 `void`，没有返回值依赖
- 唯一副作用是「少写一份日志文件」——不影响业务
- 避免写 trampoline（varargs 的 trampoline 很难做对）

# 8. 硬核技巧库：对抗手段逐个破解

## 8.1 壳（Packers）—— 先分类，再决定破不破

> ⚠️ **核心认知：不是所有壳都一样。"加密壳"能脱，"虚拟化壳"不能还原。**
> 搞混这两者，会在不可能的目标上耗掉几天。

### 8.1.1 壳的四类分级

| 类型 | 代表 | 原理 | 可破性 | 耗时 | 本次是否验证 |
|------|------|------|:------:|------|:------------:|
| **压缩壳** | UPX / ASPack / MPRESS | 只压缩，运行时解压到内存 | ✅ **容易** | 分钟 | ❌ 未遇 |
| **加密壳** | ASProtect / PECompact / Enigma | 加密代码段，运行时解密 | ✅ **可破** | 小时 | ❌ 未遇 |
| **虚拟化壳** | **VMProtect** / Themida / CodeVirtualizer | **x86 指令编译成自定义字节码，在 VM 里执行** | ⚠️ **不能"还原"** | 天~周 | ✅ **本次遇到** |
| **硬件绑定** | 部分商业壳 | 绑定 CPU/主板/网卡 | ❌ 换机跑不了 | — | ❌ 未遇 |

### 8.1.2 为什么 VMProtect special —— 这不是"加密"，是"重新编译"

```
普通加密壳：
  原始 x86 指令 ──加密──> 密文 ──运行时解密──> 原始 x86 指令（完整还原）
                                                    ↑ 可以 dump 出来 ✅

VMProtect：
  原始 x86 指令 ──编译──> VM 字节码 ──VM 解释器执行──> 效果相同
                              ↑              ↑
                    原始指令【已不存在】   只能逐条跟踪语义
                    无法"解密"回来         得不到干净函数体
```

> 📌 **结论：「脱壳还原函数体」在 VMProtect 上不是"难"，是"信息论上不存在"。**
> 这不是技术不够，是产物本身不保存原始指令。

### 8.1.3 实际可行的 4 条路径

| 路径 | 可行性 | 说明 | 本次验证 |
|------|:------:|------|:--------:|
| **1. 静态脱壳** | ❌ | VMProtect 无解（其它壳可以） | ✅ 确认失败 |
| **2. 动态跟踪 VM** | ⚠️ | 能跑，但每步都在解释器里，**极慢**（一个函数几万步），要从 handler 反推语义 | ❌ 未试 |
| **3. 内存 dump** | ⚠️ | 能 dump「VM 解释器 + 当前字节码」，但**不是原始函数** | ❌ 未试 |
| **4. 边界 hook（绕过）** | ✅✅✅ | **不打函数体，从输入/输出下手** | ✅ **本次成功** |

**路径 4 是本手册的核心思想：**

```
不打 SendFileCardToService（VMProtect 保护）
        ↓
改看它的「输出」→ 日志里就有完整请求参数
        ↓
一次拿到 API_ENDPOINT + {"uid","url"}
```

| 观察点 | 能拿到什么 | 本次验证 |
|--------|-----------|:--------:|
| 日志函数 | 请求参数、URL、错误码 | ✅ |
| 网络层（libcurl / HTTP DLL） | URL + Body + Headers | 🟡 部分 |
| 内存（JSON 字符串） | 构造好的请求体 | ✅ |
| API 调用（WriteFile / CreateProcess） | 文件操作、子进程 | ❌ 未试 |
| UI 层（CEF / DevTools） | 页面内部函数 | ✅ |

### 8.1.4 决策树：什么时候真的值得破壳

```
遇到「有壳 + 加密」
│
├─ Step 1：判断壳类型
│   ├─ 压缩壳（UPX 等）
│   │    → ✅ 直接脱：upx -d target.exe
│   │
│   ├─ 加密壳（ASProtect/Enigma 等）
│   │    → ✅ 尝试脱：x64dbg 跑到 OEP → Scylla dump + 修复 IAT
│   │    → 耗时：几小时，成功率高
│   │
│   └─ 虚拟化壳（VMProtect/Themida）
│        → ⚠️ 别急，进 Step 2
│
├─ Step 2：虚拟化壳 —— 先问「我真的需要函数体吗？」
│   ├─ 只需要接口 / 参数 / 行为
│   │    → ❌ 不破壳，直接边界 hook（日志 / 网络 / 内存 / CDP）
│   │    → 成本：1 小时 vs 1 周
│   │
│   ├─ 需要核心算法（签名/加密）
│   │    → 进 Step 3
│   │
│   └─ 需要长期深入研究（要读全部逻辑）
│        → 可评估投入（≥1 周，且有失败风险）
│
└─ Step 3：需要算法时的优先级（从便宜到贵）
    ① 算法是否在壳外？
       （JS / 未保护的 DLL / 配置文件）→ 直接逆，最便宜
    ② 能否「调它」而不「懂它」？
       → CDP 调页面函数
       → 注入 DLL 调导出函数（T2a）
       → hook 调用点，让客户端自己算
    ③ 都做不到 → 才考虑破壳（动态跟踪 VM，成本极高）
```

### 8.1.5 关键洞察：「算法在壳内」≠「无法复现」

```
签名算法被 VMProtect 保护 → 不能"逆算法"
        ↓
但可以"直接调用它"：
  · CDP 调页面函数
  · 注入 DLL 调导出函数（T2a）
  · hook 它的调用点，让客户端自己算
        ↓
不需要知道算法是什么，只需要知道「怎么让它算」
```

**本次的实际对照：**
| 算法 | 位置 | 处理方式 |
|------|------|---------|
| `random` 签名（md5 + 盐） | **JS 里（明文）** | ✅ 直接逆出来 |
| `rctk-sign` | 二进制内（可能是 VMProtect） | ⚠️ 未破，改为**复用**（不绑 body） |
| `Anti-Content` | 混淆 JS | ⚠️ 未破，改为**页面内调用**（且实测服务端不校验） |

> 💡 **这条经验很值钱**：三个签名，一个逆了，两个"绕过"了 —— **没有一个需要破壳**。

### 8.1.7 如果真的要破 VMProtect（另一条专业路线）

> ⚠️ **这是独立技术领域，建议单独立项评估，不要混在「拿接口」的任务里。**

| 工具/方向 | 用途 |
|-----------|------|
| **VTIL / NoVmp** | 尝试把 VM 字节码 lift 回中间表示（成功率有限，且需版本匹配） |

> **壳不是用来"破"的，是用来"绕"的。**
> 压缩壳/加密壳 → 脱；
> 虚拟化壳 → 从边界观察行为，或直接调用它；
> 只有当「必须静态理解算法」且「无法调用」时，才考虑破壳。

## 8.3 参数过滤（启动参数传不进去）

| 现象 | 对策 |
|------|------|
| 加 `--remote-debugging-port` 无效 | 启动器过滤了参数 |
| 检查子进程命令行没该参数 | 同上 |

**解法：同名启动器替换**
```
原: target_browser.exe (2683 KB)
    ↓ 备份为 target_browser_real.exe
新: target_browser.exe = launcher.exe (158 KB)
    launcher 内部：CreateProcess(real, 原参数 + 注入参数, bInheritHandles=TRUE)
```

**关键点：**
- 必须 `bInheritHandles=TRUE`（继承 IPC 管道句柄）
- 必须等待子进程（否则父进程以为它死了）
- 会触发完整性校验提示（可容忍）

## 8.4 虚函数 hook（vtable patch）

**症状**：导出了函数、也 hook 了，但**一次都没触发**。

**原因**：C++ 虚函数通过 vtable 调用，不走导出表。

**解法：**
```cpp
void** vt = (void**)GetProcAddress(dll, "??_7ClassName@@6B@");  // vtable 符号
void* realPost = GetProcAddress(dll, "?Post@Class@@...");

VirtualProtect(vt, 24 * sizeof(void*), PAGE_READWRITE, &old);
for (int i = 0; i < 24; i++) {
    if (vt[i] == realPost) vt[i] = (void*)hook_Post;
}
```

**注意：**
- 只扫**有限槽位**（本次 24），扫太多会误伤相邻 vtable → 崩溃
- 多线程调用要**加锁**（否则 `fprintf` 同一 FILE* 会堆损坏）

## 8.5 签名算法（rctk / Anti-Content）

| 情况 | 对策 |
|------|------|
| 签名**不绑定** body/时间 | 直接**复用**（本次 rctk-sign 可复用） |
| 签名绑定 body | 逆算法，或**调内部函数算**（CDP） |
| 页面自动加（Anti-Content） | 在**页面上下文**发请求，让它自己加 |
| 服务端不校验 | 试一次不带（本次实测通过） |

**优先级：复用 > 调内部函数 > 逆算法 > 模拟浏览器**

### 8.6.1 内存扫 LOGIN_TOKEN 的实测流程（✅ 2026-10-20）

```
① 定位进程：TARGET.exe（宿主）+ target_browser.exe（--role=browser 的 browser 主进程）
   → network service / renderer / storage / gpu 进程【0 命中】，别浪费时间扫它们
② 只扫「已提交 + 可读 + 非 PAGE_GUARD」区域，8 MB 块 + 4 KB 重叠（防特征串跨块）
③ 正则：LOGIN_TOKEN["']?\s*[:=]\s*["']?\s*([A-Za-z0-9_\-./+~=]{12,400})
   命中形态：`LOGIN_TOKEN=...;Max-Age=864000;path=/;Secure;HttpOnly` 和 `Cookie: LOGIN_TOKEN=...`
④ 按命中次数排序（真值被复制多份，本次 x40~x60；碎片只有 x1~x2）
⑤ 用探针 /plateau/chat_status/mobile/get 验证，success 才算拿到
```

**值与耗时**：`windows_1-<随机>_<mall_id>_<cs_uid>`，116 字符；7 进程 ≈2.6 GB → **约 20 s**。
顺手白拿 `mall_id` / `cs_uid`（和 `csid: cs_<mall_id>_<cs_uid>` 一致，可作为交叉验证）。

**关于「反复扫描触发刷新」——本轮未复现（结论已改写）：**
```
2026-10-20 连续 6 次全量扫描（11 分钟内），pass_id 字符串完全相同，探针每次通过。
→ 至少同一登录态内可以放心重复扫描；「扫一次就失效」不成立。
```

**但同日确实发生了一次「登录态已失效」（归因未定，别写成因果）：**
```
10:52 工作台弹「登录态已失效」→ 用户重新登录 → LOGIN_TOKEN 换值
  sha256[:10] e827ef52ea（windows_1-SnEv…） → 71bd1cf34e（windows_1-Ds8w…），长度均 116
内存里新旧两份并存：新值命中 x36，旧值仍 x10 → 不按命中次数排序就会先试到过期值
```
- **结构性排除**：`ReadProcessMemory` 纯读，目标进程无回调，**不可能**让服务端会话失效。
- 🟡 可疑点（按可能性）：①服务端 TTL/风控；②**探针 UA 与客户端不一致**（此前用的通用 Chrome UA）——
  「同 cookie 换环境」是风控常见触发点，已改为客户端同款 UA；③客户端 `/restorelogin=true` 恢复流程失败。
- 加固：结构过滤剔碎片 + **默认只发 1 次探针** + UA 对齐客户端 + 不落盘不缓存。


## 8.6.2 请求信封：`{"data": {...}, "client": N}` —— 30000 的头号原因（✅ 2026-10-20）

> 同一个端点，**平铺 body 一律 30000，套上信封立刻 success**。踩过就知道值多少钱。

```
❌ {"page":1,"size":5,"offset":0,"endTime":...}            → 30000（试了 7 种组合全错）
✅ {"data":{"page":1,"size":5,"offset":0,"endTime":...},"client":1}   → success
```

怎么定位的（可复用套路）：
1. 前端 bundle 里搜端点字符串，找到调用点：`this.request(path, {data: e, client: r.WEB})`
2. 再搜传输层实现：`J = function(e){ return function(t,n,r){ ... var p = merge(defaultData, n) ...} }`
   → **第二参数 `n` 整体就是 body**，所以 `{data, client}` 被原样发出去
3. `client` 是枚举：`e[e.WEB=1]="WEB"`（IOS=2 / ANDROID=3 / MINIAPP=4 / WIN=5 / MAC=6）

**附带发现（2026-10-20）**：`latest_conversations` 的列表项只有「最后一条消息」，**不含 `conv_id`**；
桌面端二进制里也**没有按 uid 发文本的 HTTP 端点**（只有 `API_ENDPOINT` 视频卡片、`API_ENDPOINT2` 商品卡）。
→ 文本消息只能走 WS `WS_SEND_FN`，这正是文档 §3.1 的老结论，被二进制字符串表再次证实。

# 9. 上下文管理：防重复研究的研究日志规范

> **这一章解决「上下文压缩」这个 AI 逆向的核心痛点。**
> 长任务必然被压缩，压缩后 AI 会「忘记」之前试过什么 → 重复劳动。

## 9.1 一页纸原则

**只维护一个主文档**：`RESEARCH_PROGRESS.md`

```
❌ 不要散落成 10 个 .md（本次踩过，后来归档了 17 个）
```

```markdown
### 2. API 端点
### 3. 签名机制

|------|------|------|
```

## 9.3 记录纪律（5 条）

| # | 纪律 | 为什么 |
|---|------|--------|
| 1 | **一旦有确定结论，立刻写进文档** | 别攒着，压缩后全丢 |
| 2 | **失败也要记，带错误码/现象** | "Frida 失败"没用；"Frida 报 ProcessNotRespondingError（pid 126680），VMProtect 拦注入"才有用 |


# 10. 陷阱清单（血泪）

| # | 陷阱 | 后果 | 正确做法 |
|---|------|------|---------|
| 1 | **IFEO 包装同一个 exe** | 无限递归，数千进程爆炸 | 绝不这么做；用启动器替换 |
| 2 | **替换被签名校验的 DLL** | 启动崩溃 | 内存内联 patch |
| 3 | **在 CEF 上折腾代理** | 浪费数小时（5 种全失败） | 直接 CDP 或日志 hook |
| 4 | **虚函数用导出 hook** | 一次都不触发 | patch vtable |
| 5 | **`.def` 导出名加引号** | 错误 127，应用起不来 | 不加引号 |
| 6 | **多线程写同一 FILE*** | 堆损坏闪退 | `CRITICAL_SECTION` |
| 7 | **vtable 扫太宽** | 误伤相邻类，崩溃 | 只扫前 24 槽 |
| 8 | **反复内存扫描** | 🟡 原以为会刷新凭据 | **2026-10-20 实测未复现**：6 次连扫同值且有效 → 可以重复扫；只需注意「提取后尽快用」与「跨重启是否换值待验证」（§8.6.1） |
| 9 | **相信"技术文档"的代理方案** | 定制客户端根本不遵守 | 先小成本验证 |
| 10 | **忘了 UI 自动化是禁的** | 白做 | 明确目标是纯协议 |
| 11 | **PowerShell 写 JSON 带 BOM** | Python 解析失败 | `utf-8-sig` 读 |
| 12 | **PowerShell 传含引号参数** | 引号被吞 | 写 `@args.json` 文件 |
| 13 | **MCP 进程退出** | 浏览器跟着关闭 | 常驻守护 + 命令文件 |
| 14 | **只 hook 一层网络库** | 漏掉其它路径的请求 | 递归看依赖链 |
| 15 | **`ptr(hexString)` 按十进制解析** | 静默读到错误地址，所有"扫描 0 命中" | 见 §14.1 |
| 16 | **假设文件 ImageBase = 运行时 base** | 虚表/函数地址全错，hook 静默不触发 | 见 §14.2 |
| 17 | **用"用户可见的名字"当抓包锚点** | 该字段根本不在这个请求里 → 永远 0 命中，误判探针坏了 | 见 §14.6 |
| 18 | **栈扫描当主路线** | guard page 崩 + 浅栈/跨线程，命中率极低 | 见 §14.5 |

## 13.1 第一步永远是：凭据存在哪？（✅ 三级来源 + 判定实验）

> 任何「需要登录态」的功能，第一件事不是找接口，是**把凭据拿到手且可自动复现**。
> 凭据拿不到，后面全是空转。

```
拿到目标后，按这个顺序做「判定实验」（每步都是几分钟）：

① 磁盘上有没有？
   找 profile 目录：命令行里的 --user-data-dir / %LOCALAPPDATA%\<App> / %APPDATA%\<App>
   ├─ Chromium 系：<profile>\Network\Cookies（SQLite）
   │   查什么：select host_key,name,length(value),hex(substr(encrypted_value,1,3))
   │   ├─ 行存在且 value 非空      → 落盘了，直接读（最省事）
   │   ├─ 行存在但只有 v10/v11 密文 → 需 DPAPI 解密（同用户即可）
   │   └─ 压根没有这一行           → ★ 会话 Cookie，只在内存里 → 走 ③
   └─ 自定义格式：搜 *.db / *.bin / prefs / token 文件

② 能不能从调试接口拿？
   能开 DevTools / CDP → Network.getAllCookies（最可靠，但要先解决开不开的问题）

③ 进程内存扫描（最后但常常唯一可用）
   见 13.2，注意 SQLite 里没有 ≠ 服务端没 Cookie，而是它 is_persistent=0
```

**通用判据**：`is_persistent=0` / `has_expires=0` 的 Cookie **不会落盘**，
所以"从磁盘读"这条路在会话型票据上必然失败——这不是你方法不对，是数据不在那。

【证据来源】某电商工作台：`Network/Cookies` 只有 3 行，`length(value)=0` 且全是 `v10` 密文，
目标票据根本不在表里 → 直接判定"内存唯一路径"，省掉一整轮 DPAPI 折腾。

## 13.2 内存取票据：三个必须处理的现实问题（✅ 实测）

```text
只扫「已提交 + 可读 + 非 PAGE_GUARD」区域（VirtualQueryEx 逐段枚举）
按 8 MB 分块 + 4 KB 重叠（特征串会跨块）
用 ReadProcessMemory 读，绝不写、不注入、不改内存
```

**问题 1：多进程里到底扫哪个？**
> 先**全扫一遍看命中分布**，再固定只扫命中的那几个。
> 命中往往集中在宿主进程 + 浏览器主进程；network / renderer / gpu 常常是 0 命中。
> 固定名字省时间，也降低"扫一堆无关进程"的误报。

**问题 2：命中的字符串是碎片还是真值？**
> 用**结构过滤**，别用"取第一个"。
> 真值有稳定结构（前缀 + 随机串 + 分隔 + 后缀）；碎片通常是长度不对、后缀缺失的截断。
> 加一条正则把"形态完整"的挑出来，探针次数立刻从 N 降到 1。

**问题 3：怎么确认取到的是"活的那份"？**
> **按命中次数排序**。某个值被复制得最多，通常就是当前正在用的那份。
> 重新登录后，旧值副本**仍留在堆上**，但命中次数明显更低（实测 x10 vs x36）。

**问题 4：怎么验证？**
> 拿一个**只读的、幂等的**业务接口当探针（如状态/心跳/用户信息）。
> 返回 200 + 业务成功码才算拿到；不要靠"字符串看着像"。

## 13.3 凭据生命周期与「掉线归因纪律」（✅ 方法 / 🟡 具体归因）

**已知规律（换目标也成立）：**
| 现象 | 结论 |
|---|---|
| 重新登录后票据换值 | 正常。工具必须每次现取，**不能缓存** |
| 旧值还留在内存里 | 正常。靠"命中次数"分辨新旧 |
| 票据带 `Max-Age=10天` 却几小时就失效 | 服务端可提前失效，`Max-Age` 不代表可用时长 |

**掉线归因的正确姿势：**

```
第 1 步：能不能「结构性排除」某个嫌疑？（见 13.8）
        例：ReadProcessMemory 是纯读，目标进程无回调 → 不可能让服务端会话失效
第 2 步：把时间线排出来
        「我做了什么」 vs 「什么时候失效」 —— 时间吻合才有嫌疑
第 3 步：对每个嫌疑做变量控制
        UA / Referer / Origin 是否与客户端一致？
        是否建立了第二条同账号连接（WS/长连接/RPC）造成互踢？
第 4 步：写下「归因表」，允许结论是"未定"
```

**最容易踩的坑（换任何目标都会踩）：**
> **用默认 HTTP 客户端 UA 打业务接口。**
> 很多库（urllib/requests 的默认 UA、`Python-urllib/3.x`）会暴露"不是客户端"。
> 同一票据出现「客户端 UA ↔ 脚本 UA」交替，是风控识别"会话被复制/多端使用"的典型特征。
> **一条规矩：请求头三件套（UA / Referer / Origin）一律照抄客户端。**

## 13.4 前端代码：三条获取路径（✅ 全部走通过）

|---|---|---|---|
| ① 本地资源目录 | 命令行里有 `--*-local-root-path` / `--user-data-dir` | 直接 grep 本地 JS | 分钟 |
| ② **远端页面拉取** | 本地没有（页面是服务端渲染的） | 用**已拿到的凭据 + 客户端 UA** 把 `index.html` 和 bundle 下下来落盘，再静态读 | 10 分钟 |
| ③ CDP | 需要运行时信息（DOM、闭包、动态参数） | `Runtime.evaluate` 调页面函数 / hook fetch | 需先能开 DevTools |

**② 是最容易被忽略的一条**：很多人以为"要抓就必须动态调试"，其实
**只要有合法登录态，前端代码就是可以静态下载的资产**。

```text
步骤：GET 页面 → 解析 <script src> → 逐个下载到本地 js/ → grep 端点与关键字
注意：带上客户端的 UA / Referer / Origin，否则可能拿到拦截页或 403
```

【证据来源】本地 `Plugins\web\` 里搜 `/plateau/chat/` 零命中；
从远端 `…/chat-merchant/index.html` 拉下 `index.bundle.js` 后，端点、参数、
枚举值全在里面。

## 13.5 错误码驱动的参数探测法（★ 本章最值得带走的一条）

> 不要"猜参数直到成功"，要**用错误码的语义变化当地图**。

```
原则：错误码不是失败信号，是「你已经走到哪一层」的坐标。

  A 类：参数校验层错误（缺字段/类型错/形状错）
  B 类：业务层错误（字段都合规，业务拒绝：无权限/对象不存在/不满足前置条件）
  C 类：鉴权层错误（会话失效/未登录）
  D 类：成功

从 A 走到 B，说明【形状已经对了】，剩下的只是取值/对象问题 —— 这是重大进展。
```

**实操：一次只改一个变量，观察错误码是否"升级"。**

| 你改了什么 | 错误码变化 | 说明 |
|---|---|---|
| 请求体从平铺改成信封 | A → D | 形状是主因，一次解决 |
| 某字段从"字符串"改成"对象" | A（提示变具体） | 类型校验通过但内容不对 |
| 换 ID 的形态 | A → B | **形状对了**，ID 属于业务层校验 → 继续试 ID 来源，别再改 body |
| 加/去掉 AA 头 | 无变化 | 该头非必需，别浪费时间 |

**配套动作：把错误码词典写进日志文档。**
> 本次记录的词典：`1000000 成功 / 30000 参数错 / 40000 系统错 / 43001 会话失效`。
> 有了词典，下一次同类错误你自己就能读出"我在哪一层"。

## 13.6 请求信封与枚举：body 形状不要猜（✅ 7 组对照实验）

> 同一个端点，**平铺 body 全错、套上信封全对**。这类"传输层包装"必须从代码里读出来。

```text
❌ {"page":1,"size":5}                       → A 类错误（试 7 种组合全错）
✅ {"data":{"page":1,"size":5},"client":1}    → 成功
```

定位手法（可复用）：
1. bundle 里搜端点字符串 → 找到调用点：`this.request(path, {data: e, client: r.WEB})`
2. 再搜传输层实现 → 看它怎么组装 body：
   `J = function(e){ return function(t, n, r){ var p = merge(defaultData, n); ... } }`
   → **第二个参数 `n` 整个就是 body**，于是 `{data, client}` 被原样发出去
3. 枚举值也从代码读：`e[e.WEB=1]="WEB"` → `client=1`，不要试 `"web"` / `2` / `"1"`

**通用规律**：凡是有"客户端类型/端类型"的接口，几乎都有这层包装；
先假设存在信封，再验证，比逐个字段试快一个数量级。

## 13.7 HTTP 走不通时：WS/长连接落地五步（✅ 端到端跑通）

> 桌面 IM 类应用**文本消息常走长连接**，HTTP 只用于卡片/文件。
> 判断信号：HTTP 的 send 端点参数怎么试都是 A/B 类错误，且二进制里根本没有"按 uid 发文本"的路径。

```
① 找取票端点：搜 /token / getToken / auth → 通常返回 {token, use_ip}
② 拼连接 URL：代码里能直接读到，形如
   wss://host/?access_token=<token>&role=<角色>&client=<端类型>&version=<build>
③ 握手带上 Cookie + 客户端 UA + Origin（缺一可能被拒或被视为异常端）
④ 帧结构从代码抄：通常 {"cmd":"<动作>","request_id":N,"message":{...},"random":"<签名>"}
   · request_id 是关联响应的关键 → 用随机数，比"看谁先回来"可靠
   · 签名算法一般在 bundle 里明文（拼接顺序 + 硬编码盐）
⑤ 用 request_id 匹配响应；再回读列表/历史确认真的生效（双证据）
```

**纪律：** 用完立刻 `close()`，不常驻、不轮询。
同账号第二条长连接**很可能与客户端互踢**（单点登录语义），这是掉线的高危嫌疑之一。

【证据来源】某工作台：`getToken` → `wss://…/access_token=…&role=<role>&client=web`
→ `{"cmd":"send_message",…,"random":md5(...)}` → `{"response":"send_message","result":"ok"}`；
随后会话列表的"最后一条消息"同步变化，构成双证据。

## 13.8 「结构性排除」作为一种论证方法（✅ 值得刻意练习）

> 逆向里最常见的浪费：把"没验证过"当成"可能是原因"。
> **能用机制否掉的，就别再用试错去排。**

| 嫌疑 | 结构性论证 | 结论 |
|---|---|---|
| 内存读导致会话失效 | `ReadProcessMemory` 无回调/无通知机制，目标进程无法感知被读 | 不可能 |
| 替换文件导致崩溃=代码错 | 先确认有无完整性校验（`digital_sign`/`md5checker`/sentinel） | 先排除校验，再怀疑代码 |
| 端点参数错=算法不对 | 若返回的是"参数错误"而非"签名错误"，算法可能根本没被调用 | 先修形状，别动算法 |
| 代理抓不到=证书问题 | CEF 可能硬编码忽略系统代理 | 排除整条路线，别装证书 |

写法建议：在日志里写 **"结构性排除：X，理由是机制 Y"**，而不是"试了没事"。
后者下次还得再试一遍。

## 14.1 注入类工具链的静默失败清单 ✅

## 14.2 运行时重定位 + 「文件 ↔ 内存」对照实验 ✅

**别假设 ImageBase。** 单体客户端常见 base 不是 `0x400000`（实测见过 `0x920000`）。

```js
// 换算公式：运行时地址 = module.base + (文件VA - 文件ImageBase)
const exe  = Process.getModuleByName('target.exe');
const rva  = fileVA - fileImageBase;
const addr = exe.base.add(rva);
```

### 对照实验（10 分钟，一次性回答三个问题）

挑一个**必然含绝对指针**的文件 VA（虚表最理想），读 32~64 字节，与磁盘同 RVA 的字节比对：

```python
# 输出：file hex / mem hex / 是否相同
# 判读：
#  完全相同        → 磁盘文件可信，静态分析全部有效
#  结构同、指针差  → 该差值 = 运行时重定位增量，磁盘文件仍可信
#  完全不同        → 运行时被解密/改写，必须 dump 内存再分析
```

这一条同时验证了：**① 真实 base ② 重定位增量 ③ 能不能拿磁盘文件做静态分析**。
省掉后面所有"这个地址怎么读不出来"的困惑。

## 14.3 从 RTTI 反查虚表（MSVC，x86 / x64）✅

虚函数 hook 的正确入口。比猜特征码、比扫内存找 vtable 都稳。

```text
① 类型名字符串（.?AVClassName@@ 这种）所在 VA
② TypeDescriptor = 名称VA - 8   (x86)   /  - 16  (x64)
③ 在 .rdata/.data 里搜 "TypeDescriptor 的 4/8 字节地址"
     → 命中的位置在 CompleteObjectLocator(COL) 里（x86 为 COL+12）
     → 校验：COL 起始 4 字节 signature == 0
④ 再搜 "COL 的地址"
     → 命中的 dword 的【下一个 dword】就是 vftable
⑤ 读 vftable 的前 16~24 个槽，过滤出落在 .text 的
```

要点：

- **多继承**：vtable 数组里会出现 `.rdata` 指针（第二/第三基类的子 vtable），hook 时必须跳过，否则 `Interceptor.attach` 直接报错。
- **slot 归位**：同一个模板的多个实例化，**前面若干 slot 完全相同**（基类），**后面几个不同**（每类的重写方法）。对比两个实例就能定位"业务方法"在哪几个 slot。
  - 例：`Cmd<A,Rsp>` 与 `Cmd<B,Rsp2>` 的 slot 0–7 一致，8/9/10 不同 → 这三个就是 `取命令号 / 请求序列化 / 响应解析`。
- **x86 thiscall**：`this` 在 `context.ecx`，`args` 只是栈参数（`args[0]` 通常是第一个形参或返回值槽位，不是 this）。x64 才在 `args[0]=rcx`。

## 14.4 内存里的 C++ 对象怎么读（不调函数也能拿明文）✅

定位到一个对象指针后，**不序列化、不解密**，直接按布局挖字段。

**MSVC `std::string`**

| 位宽 | 布局 | 取值规则 |
|---|---|---|
| x86 | 24 B：`union{char buf[16]; char* p}` + `size@16` + `cap@20` | `cap >= 16` 用 `p`，否则用对象内 `buf` |
| x64 | 32 B：`union{char buf[16]; char* p}` + `size@16(8B)` + `cap@24(8B)` | 同上 |

**`RepeatedField<T>`**：`{ T* elements; int current_size; int total_size; }`（x86 12 B / x64 16 B）
→ 这就是"成员列表 / 参数数组"。

**挖掘套路（O(字段数)，不需要结构体定义）**：

```text
for off in 0 .. objSize step 4:
    size = read32(obj+off+16); cap = read32(obj+off+20)
    if 0 < size <= 512 and size <= cap <= 4096:
        dataPtr = (cap >= 16) ? read32(obj+off) : obj+off
        s = readUtf8(dataPtr, size)
        if printable(s) >= 90%: 记录 (off, s)
```

再给结果分档，噪声立刻下降：

| 档 | 规则 | 含义 |
|---|---|---|
| `VID/ID` | `^\d{6,}$` 或 `^[A-Za-z0-9_-]{6,}$` | 用户/实体标识 |
| `CJK` | 含 ≥2 个汉字 | 显示名 / 标题 |
| 其它 | 丢弃 | — |

**另一条通用识别法**：对象首 dword 若指向「某模块的 `.rdata`」，它就是多态对象；顺着读 vtable 就能判断它属于哪个类（配合 §14.3 的 RTTI 表）。

## 14.5 栈扫描为什么经常是死路 ✅

想"从网络写函数往回调栈找明文"，会同时踩三个坑：

1. **guard page**：`esp.readByteArray(0x10000)` 必然跨过栈顶 → `access violation`。
   正确：先 `Process.findRangeByAddress(esp)`，可读上限 = `range.base + range.size - esp`，再按 4 KB 分块、遇错即停。
2. **浅栈**：实测某些线程 esp 距栈顶只有 **≈6 KB**，能读到的"更老的帧"就这么点。
3. **跨线程**：真正构建请求的那层代码可能在另一个线程上（SDK 的工作线程），它的帧**根本不在这个栈上**。

> 判定：如果 `[scan]` 日志里 `stackWords` 常年只有几百（说明只能读几 KB），就别在栈上继续投入了。
>
> 替代优先级：**hook 一个"接收该对象的函数"**（构造函数 / 序列化入口 / 业务方法）＞ 栈扫描 ＞ 堆扫描。

## 14.6 锚点选择的三个反模式 ✅

抓明文时用字符串当锚点，是最高效也最容易翻车的做法。

| 反模式 | 现象 | 真因 | 正确做法 |
|---|---|---|---|
| 用**用户可见的名字**当锚点 | 5 轮探针 0 命中，怀疑探针坏了 | 该名字是**服务端生成**的，请求里根本没有 | 用"必然出现的字段"（ID、成员列表），或改用**结构识别** |
| 忽略**操作顺序** | 抓不到创建请求 | "创建时命名" 与 "先创建后改名" 是**两个不同接口** | 先问清操作序列，再决定抓哪个请求 |
| 用**展示文案**匹配 | 偶发命中，不稳定 | 文案有多语言/多版本 | 匹配 ID / 协议字段 |

**结构识别**（无锚点兜底）：扫栈上指针，命中"首字节是合法 protobuf tag（`08/0a/12/1a`，字段号 1–15，wiretype ≤ 2）+ 长度 < 4 KB + 可打印比例 < 90%"的 buffer 就 dump。命中率高但噪声大，配合 §14.4 的分档过滤。

## 14.7 「探针在跑」≠「探针有效」—— 自检协议 ✅

每次挂新探针，先过这 5 条：

```
□ 打出 [ready]（证明 script.load() 成功）
□ 对"已知一定会发生的流量"打出至少 1 条事件（证明触发点选对）
□ 输出文件的 mtime 在近期（证明宿主没卡死）
□ 事件计数在增长，且字段（长度/线程/地址）有变化（证明不是同一个事件重复）
□ 有一个"必然命中"的对照锚点（已知会出现在 payload 里的字符串/ID）
```

做不到第 2 条时，先在一把**高频 API**（如 `GetTickCount`）上跑同一套骨架，验证读取/换算/打印链路。

## 14.8 大单体 PE 的静态分析工作流（不装 IDA 也能干）✅

单体客户端常见 200–400 MB 单文件，装重型工具反而慢。

```python
# 2) 段表做 VA ↔ 文件偏移 双向映射（关键，别手算）
for s in pe.sections:

pe.parse_data_directories([pefile.DIRECTORY_ENTRY['IMAGE_DIRECTORY_ENTRY_EXPORT']])

# 4) 导入表回答"这个模块用了哪个库"（谁 import 谁，比字符串可靠）
```

- **`bytes.find` + 段映射** 能替代 80% 的"我只想找这个字符串被谁引用"（配合 §14.3 的引用搜索）。

## 14.9 加密体的边界判定（不破算法也能定位）✅

先回答"**加密发生在哪一层**"，再谈算法。

| 观察 | 推论 |
|---|---|
| 所有 `Content-Length` 两两之差都是 **16 的倍数** | 分组密码（块长 16），且有 PKCS#7 填充 |
| body 起始是**固定 N 字节常量**，之后是一段与某个 header 字段**逐字节相同**的数据 | 信封结构：`固定头 + 已编码头 + 密文 + 尾` |
| 参数写库的调用序列里**没有** `POSTFIELDS`，只有 `POSTFIELDSIZE` | body 不走常规字段 → 加密在更上层，抓库函数没用 |
| 同一个 header 字段时而 30 B 明文、时而 272 B 高熵 | 存在"短格式/长格式"两条分支，先只攻短格式 |

**判定实验**：把 header 字段 base64 解码后与 body 做十六进制比对，能直接量出"头有多长、密文从第几字节开始"。这比盲猜偏移可靠得多。

```
1. 明文日志侧信道            ← 最优，先找日志目录/日志函数（§6）
2. 前端 bundle / CDP          ← 有 CEF/Electron 时（§4.1）
```

## 14.11 和人协作的纪律 ✅

## 14.12 两层离线自测：把「真机验证」压缩到一次 ✅

> 这一节是 §14.11 的执行手段。人只该验证**结论**，不该用来跑**单测**。

真机验证贵、不可重复、状态还可能被上一次搞坏。所以逻辑必须先在两处跑通：

### 第一层：Node 假运行时（零风险，任意造数据）

把注入脚本里的 JS 原样抽出来，在 Node 里用桩替代 Frida 全局，然后喂**真实抓到的**数据：

```js
// scripts/66_js_harness.js 的骨架
global.ptr = makePtr;            // 用 Map 模拟地址空间
global.Memory = { alloc, writeByteArray };
global.Interceptor = { attach(t, cb) { attachList.push({t, cb}); } };
global.Process = { getModuleByName: () => ({ base: makePtr(0x920000) }) };
global.send = o => sends.push(o);
global.recv = (t, cb) => { recvHandlers[t] = cb; };

eval(fs.readFileSync('generated.js', 'utf8'));          // 就是真脚本那份 JS
recvHandlers['cfg']({payload: {mode: 'dropLast'}});      // 配置
slot8Hook.onEnter([]);                                   // 进入业务上下文
serHook.onEnter.call(ctx, [{toUInt32: () => stdAddr}]);
serHook.onLeave.call(ctx, makePtr(0));                   // 触发改写
// 断言：改写后的字节能被同一个解析器重新解析，且字段符合预期
```

价值：**改写逻辑的 bug 100% 在这一层暴露**，包括「把裸字节塞进节点列表导致 emit 读到 undefined」这类。

### 第二层：真实运行时 + `rpc.exports`（不打扰人）

同一份 JS 加载进**真实进程**，把改写核心做成 `rpc.exports` 导出，用合成数据调用：

```python
sc = s.create_script(js + '''
rpc.exports = { rewrite: function (hex, mode, members) {
  CFG = {mode: mode, members: members};
  const buf = new Uint8Array(hex.match(/../g).map(h => parseInt(h, 16)));
  const r = applyRewrite(buf);
  return JSON.stringify({action: r.action, note: r.note, hex: hexOf(r.bytes),
                         memRoundtrip: writeThenReadBack(r.bytes)});
}};''')
print(sc.exports_sync.rewrite(plain_hex, 'dropLast', []))
```

价值：抓**运行时差异**（API 改名、引擎行为、内存写权限）。本次就靠它抓到 Frida 17 移除 `Memory.writeByteArray`。

### 关键设计：改写核心必须是**单一函数**

```
applyRewrite(raw) -> {bytes, action, note}     ← 唯一实现
    ↑ hook 调用              ↑ rpc 自测调用      ← 同一份代码
```

否则自测通过 ≠ 真机通过，白测。

### 顺序铁律

```
离线逻辑对 → 真实运行时跑通 → 才叫人做动作
任何人做一次动作，都必须能一次性判定成立/不成立
```

> **能"读到对象"就绝不"解密流量"；能"hook 业务方法"就绝不"扫栈"。**
> 加密是墙，对象是门。门一直在，只是要找对类的虚表。

# 15. 请求改写与「命令身份」——协议层提权的三个层次

> 来自一个隧道式 IM 桌面端：所有 CGI 走同一个 HTTPS 端点，命令 id 与 payload 一起加密。
> 这一章解决一个通用问题：**当我想让客户端替我做一件它没被点过的事，改哪一层最划算？**

## 15.1 三个改写层次（成本递增，成功率递减）

| 层次 | 做法 | 需要知道 | 成功率 | 副作用 |
|---|---|---|---|---|
| **① 序列化后明文** | hook 序列化函数，改它返回的 `std::string` | 明文 schema | 高 | 无 |
| ② 对象字段 | 直接写 C++ 对象成员 | 对象内存布局 | 中 | 布局一改就崩 |
| ③ 密文 + 信封 | 自己加密、自己组信封 | 算法 + 密钥 + 命令头 | 低 | 易被服务端拒 |
| ④ 换明文「冒充」别的命令 | 把 A 命令的明文换成 B 的 | 无（看似最省事） | **通常为 0** | 见 15.3 |

**优先①，别碰②**。①只需要 schema，不需要对象布局，也不需要碰加密。
本次建群就是①：`hook 序列化函数 → 拿到明文 → 改写 → 写回 std::string → 客户端自己加密发送`。

## 15.2 proto-lite 没有 descriptor 时怎么拿 schema

现象：`strings`/全量扫描都找不到 `FileDescriptorProto`，RTTI 里也没有 message 元信息 ⇒ 静态链接的 protobuf-lite，**没有反射**。

唯一可靠来源是**线上字节**。反推手法：

```
1) hook 序列化出口，把明文 hex 落盘（一次能拿全字段）
2) 写一个宽容的 wire-format 解析器：按 key 拆 field/wiretype，不做类型断言
3) 造差异：同一个请求，用不同参数各触发一次，对比字段值
   （本次：选 2 人 vs 选 1 人 → 只有 field 2 变化 → 它就是成员列表）
4) 闭环验证：改写 → 重新解析 → 断言目标字段变成期望值
```

**wiretype 判断铁律**：`wt=0` 是 varint，**不要假设所有 id 都是字符串**。
本次成员 vid 是 `varint uint64`，早期按 ASCII 数字串去匹配，结果 `vids=` 恒为空、改写永远不生效。

## 15.3 「换明文就能换命令」——这个假设怎么快速证伪

直觉很诱人：信封头恒定 ⇒ 命令类型应该由明文决定 ⇒ 换掉明文就能换命令。
**先做这三个观察，再决定要不要写代码：**

| 观察 | 若成立 ⇒ |
|---|---|
| 两种命令的明文 **schema 差异巨大**（一个 field1 是 varint，另一个是 `"create"` 字符串） | 命令类型不可能只由明文表达 |
| 信封头在多命令间**完全一致** | 命令类型也不在显式头部 |
| `密文长度 − 明文长度` **远大于**分组填充所需 | 有额外头部被一起加密 |

三条同时成立 ⇒ **命令身份在加密体内的命令头里**，换明文只会被服务端当作原命令解析并丢弃。
本次实测正是如此：把 8 字节心跳换成 82 字节建群明文，客户端照常发出，服务端按心跳处理，群没建出来。

> 教训：**先花 5 分钟做证伪观察，别先花 2 小时写注入器。**

> ### ⚠️ 2026-10-22 更正（重要，先读这段再看上面的结论）
>
> 上面「换明文只会被服务端当作原命令解析并丢弃」这句，**结论对了、机理错了**。
> 第二天把同一个目标打到成功（`RetCode: 0`、零界面建群）之后复盘发现：
>
> - 那次"客户端照常发出、群没建出来"，真实原因是**注入没生效**——换成心跳载体的是垃圾字节
>   （`std::string` 结构体被 JS GC 回收，见 §16.1），服务端回的是 `-2003`（空错误文案）。
> - 改用**空明文类**命令做载体、并把载荷换成合法 `create` 明文后，服务端立刻按建群解析，
>   回的是 `-3066 外部成员无法加入内部群聊` —— 说明**命令身份可以由「载荷首字段 + 通道字节」表达**，
>   并不存在一个"不可见的命令头"在否决你。
> - 真正让"换明文"看起来失效的，是**有些命令类被替换后根本不会发出去**（encoder 产物生成、
>   但 10 分钟 55 次写操作里 0 次上线），见 §16.2。
>
> **修订后的规则**：换明文可行，但分两步验证——①先证明这个载体一定会发（CL 指纹核对）；
> ②再证明载荷合法（服务端回可读文案即过关）。两条都过，才谈"命令身份不可伪造"。

## 15.4 本地 ID 的逆向：能自铸 ID 就不用等响应

很多客户端的会话/对象 id 是**本地生成**的，格式往往是「编码套编码」。本次：

```
ObjIdSample0x9f3
  → base64url → protobuf → {1: 65537, 2: 时间戳, 3: self_vid, 4: 18}
```

解出来后立刻得到三个红利：

1. **不必解析响应**：请求发出前就知道对象 id
2. **可自铸 ID**：按同样格式生成，服务端照收
3. **反推身份**：`field 3` 在多个样本里稳定不变 ⇒ 那就是自己的 id（比到处找"我是谁"省事）

做法：把拿到的两个以上样本并排解码，**相同的字段是身份/常量，不同的字段是时间/随机**。

## 15.5 静态交叉引用走不通的判定信号

用虚表做锚点找业务入口，是常规打法（见 14.3）。它会遇到一类**硬墙**：

```
✓ vtable 写入点在 .text 里唯一存在   → 构造函数定位到了
✗ 该构造函数 rel32 调用者 = 0
✗ 该函数的 dword 地址引用 = 0（连函数指针表都没有）
✗ 加密/组装路径里出现 HeadHex 这类调试串
✗ 段表里有 .vmp0 / .themida / .enigma
```

**「有构造函数但零调用者」在正常编译产物里不可能出现。**
这不是扫描器 bug（先用已知调用点验证扫描器，见 15.7），而是 **VMProtect 把调用方虚拟化了**。

判定之后的动作：**立刻转运行时**，不要在静态侧继续挖。

## 15.6 静态失败后的兜底：抓一次调用现场

给目标方法下 hook，把「谁调它、参数怎么排」全部落盘：

```javascript
Interceptor.attach(target, {
  onEnter() {
    const ctx = this.context;
    send({
      regs: {ecx: ctx.ecx, edx: ctx.edx, esp: ctx.esp},       // thiscall: this 在 ecx
      obj:  hex(ctx.ecx, 0x60),                                // 对象头，找命令 id
      bt:   Thread.backtrace(ctx, Backtracer.ACCURATE).slice(0, 28),
      stack: Array.from({length: 32}, (_, i) => ctx.esp.add(i*4).readU32())
    });
  }
});
```

拿到 28 层栈后，回到静态侧只反汇编**这些返回地址前后几十字节**（成本极低，不用全量分析），
就能读出调用点压了哪些参数 —— 这就是复刻调用所需的全部信息。

> 定位：**静态找入口失败 → 动态抓现场 → 静态读现场**。三段式比硬啃加壳代码快一个数量级。

## 15.7 地址解析纪律：ASLR 下任何硬编码都是定时炸弹

本次真实翻车：把「文件 VA − ImageBase」当成 RVA 硬编码，客户端重启后基址变化（ASLR），
hook 挂到一个无效地址 —— **Frida 一声不吭**，探针看起来在跑，什么都没抓到，白费一次人工操作。

两条铁律：

```javascript
// 1) 地址从「结构」里取，不从常量里算
const vt   = exe.base.add(VTABLE_IMAGE_RVA);
const tgt  = ptr(vt.add(SLOT * 4).readU32());   // 虚表槽里存的就是运行时真实地址

// 2) 取完必须自检「落在可执行区间」
let ok = false;
for (const r of Process.enumerateRanges('r-x'))
  if (tgt.compare(r.base) >= 0 && tgt.compare(r.base.add(r.size)) < 0) { ok = true; break; }
if (!ok) send({k: 'fatal', v: 'not in code: ' + tgt});
```

**探针必须先证明自己挂对了**（呼应 14.7）：打一行 `inCode=true` 再让人操作。

## 15.8 判据不成立时，用控制组证伪方法本身

想验证「服务端是否接受」，不要只测未知项，**同时测一个已知必然成立的项**：

```
未知：新对象的 id 是否出现在客户端内存里 → 没出现
对照：一个已知存在的旧对象 id            → 也没出现
结论：不是"对象不存在"，而是"这个判据本身不成立"（id 不以该形式缓存）
```

单测一组数据只会得到「有/没有」，加一组对照才知道**该不该相信这个实验**。
这是把「假阴性」从结论里剔除的最低成本手段。

# 16. 载荷注入实战增补：从「改对了」到「真的发出去」

> 场景：形态 B（原生单体型，x86，约 200 MB 单体进程，自研编码器 + 双层 AES）。
> 结局：滑掉一条**空明文（心跳类）命令**的载荷，客户端自己加密发送，服务端返回成功码，
> 零界面创建出目标对象；两次独立运行均成功（服务端成功序号不同）。

> 本章只写第 14/15 章**没有覆盖**的内容，并更正 §15.3 的一条结论（见上文更正框）。
> 与形态 A（前端型）的区别：那边是 CEF/HTTP/JSON，这边是**原生 x86 + 自研编码器 + 双层 AES**。
>
> 术语：`ENC_FN` 编码器入口、`CMD_OBJ` 命令对象、`CHANNEL` 通道字节、`TICKET` 逐请求票据、
> `ERR_GATE`/`ERR_BIZ` 两层错误码。

## 16.1 注入 `std::string`：结构体本身也必须保住（本项目最贵的坑）✅

改序列化输出的标准做法是把明文字符串换成自己的。MSVC x86 `std::string` 布局：

```
+0x00  buf[16]     // 短字符串直接存在这里（SSO）
+0x10  size (u32)
+0x14  cap  (u32)  // cap >= 16 时 buf 前 4 字节是堆指针
```

```js
const keep = [];                                  // ★ 生命线：不 keep 必被 GC
function mkStd(bytes) {
  const p = Memory.alloc(0x40);
  for (let i = 0; i < 0x40; i++) p.add(i).writeU8(0);
  if (bytes.length <= 15) {                       // SSO 分支
    p.writeByteArray(bytes);
    p.add(0x10).writeU32(bytes.length);
    p.add(0x14).writeU32(15);
  } else {
    const nb = Memory.alloc(bytes.length + 16);   // 数据缓冲
    nb.writeByteArray(bytes);
    p.writePointer(nb);
    p.add(0x10).writeU32(bytes.length);
    p.add(0x14).writeU32(bytes.length);
    keep.push(nb);
  }
  keep.push(p);                                   // ★★ 结构体本身！漏了这句必炸
  if (keep.length > 24) keep.shift();
  return p;
}
```

**踩坑实录**：最初只 `keep` 了数据缓冲，没 keep 结构体。JS GC 回收后，栈上参数（`[esp+8]`）
变成悬空指针，编码器读到的是堆残渣。表现极具欺骗性：

| 你以为 | 实际 |
|---|---|
| 注入成功（size / cap 回读都正常） | 回读到的是自己的临时对象，编码器拿到的是另一块内存 |
| 载荷长度正确（112 字节） | 明文前 8 字节是 `0001113c0001113c…` 这类垃圾 |
| 服务端回 `-2003`（无错误文案） | **服务端在拒绝垃圾，不是拒绝你的协议** |

代价：**十几轮实验的全部结论作废**，一路在"加密不对 / OBJ_ID 不对 / 头字段不对"上打转。

**由此定下的硬纪律**（推广到所有注入场景）：

```
注入后立刻回读注入点，打印前 32~40 字节 hex（afterHex），与期望逐字节比。
回读不一致 ⇒ 注入没生效，禁止继续往下推理。
```

## 16.2 「注入成功」≠「请求发出」：载体命令决定成败 ✅

**这是本批最重要的新结论，也是对 15.3 的机理更正。**

同一段注入代码，换到不同命令类上，行为完全不同：

| 载体命令类 | encoder 产物 | 是否真的上线 |
|---|---|---|
| 空明文类（`plainLen = 0`，虚表 A） | 390 字节 | **会发**，连续 3 次验证，服务端按载荷解析 |
| 普通业务类（虚表 B/C/D） | 390 字节（同样正确） | **不发**。10 分钟 55 次 `SSL_write`、29 次读，**0 次**出现 `Content-Length: 390` |

判定方法（10 分钟，必做）：

```
1) 记下 encoder 产物长度（例如 390）
2) 在 SSL_write 层被动抓包，逐个打印 POST 的 Content-Length
3) 找 CL == 390 的那条：
      找到 → 载体可用
      找不到 → 这条命令的产物被丢弃 / 走了别的通道，换载体
```

工程结论：

- **优先用"空明文 / 心跳 / 固定小载荷"的命令做载体**——数量多、无副作用、发送路径最短。
- 这类命令只在**有真实交互**时出现（纯空闲只有 8 字节心跳 `08818004100118xx`）。
  因此触发器要么等（本次等过 3 分钟、也等过 20 分钟），要么用 hook 条件精确锁定
  （按虚表 / 按明文长度），**不要用"任意小命令"凑合**。
- 别用业务命令做载体：你不确定它有没有尺寸预计算、批处理归属、seq 绑定等隐藏校验。

**同时更正 15.3 的机理**：命令类型并不是藏在什么"不可见的密文头"里。实测把通道字节改成 8、
载荷首字段写成 `"create"`，服务端就按建群解析（先回业务错误 `-3066`，改对参数后回 `ok`）。
"换明文失败"的真实原因是**没发出去**或**明文是垃圾**，两者都不需要用"命令身份不可伪造"来解释。

## 16.3 用长度公式反推「线上到底发了多长」✅

先写出信封的算术关系，再谈"我们和真请求差在哪"。本批实测：

```
body   = MAGIC(5) + IV(16) + [ HEAD(256) + PAYLOAD ] + TAIL(1)
PAYLOAD= IV2(16) + roundup16(plain_len + 8)
```

于是由 `Content-Length` 可反推明文长度区间：

```
plain_len ∈ [CL - 285 - 8, CL - 285 + 7]      // 本批常数：5+16+256+1+16 = 294 → 285 需按实际调整
```

实际用法：真建群 `CL:406`，我方 `CL:390`，差 16 字节 ⇒ 明文差 16 字节 ⇒ **客户端在 encode 之后
还套了一层**（当时假设是 22 字节前缀）。这个差值让我们避免了一次错误方向的长跑。

但更有价值的是后半句：**算完之后要问"这个差异重要吗"**。
后来证明服务端接受 390 的版本，那 22 字节前缀根本不需要复现。
**先算，别猜；算完可能发现你原本要追的东西不是必需的。**

## 16.4 双层信封与「能读错误文案」的复利 ✅

本批的两层（同一把 16 字节 ASCII key，CBC，IV 前置）：

```
应用层   : base64( IV(16) ‖ AES-CBC( protobuf ) )
传输层   : MAGIC ‖ IV(16) ‖ AES-CBC( 256 字节头 ‖ 业务载荷 ) ‖ 0x2f
响应      : 与请求同构；头里 RetCode / 附加数据长度 / errmsg
```

只要能把响应解出来，排查效率立刻翻倍——因为**服务端会告诉你它为什么不高兴**：

```
f7 = RetCode      0 / -2003 / -3066
f8 = 附带数据长度
f9 = errmsg       空串 或 "外部成员无法加入内部群聊"
f19= 25 位序号    用于对齐是同一条请求的响应
f14= 会话密钥加密的对象信息（不是静态 key，别硬解）
```

**没有解密能力时**，你只能看"成功/失败"；**有了解密能力**，你能看到"它说成员是外部的"。
后者一步顶前者十轮。

## 16.5 错误码分层就是进度条（把"失败"重定义）✅

| 返回 | 含义 | 你走到哪 |
|---|---|---|
| `-2003` + **空** errmsg | 信封/格式层就不认 | 门都没进 → 先查注入回读（§16.1） |
| `-3066` + **有语义** errmsg | 信封 OK，业务校验拒绝 | 已进门 → 只剩业务规则 |
| `0` + `"ok"` + 附带数据 | 完成 | 收工 |

**这是本项目最重要的认知转变**：错误码从"空文案"变成"有文案"，不是又一次失败，而是
**一次实质进步**，应该立刻把方向从"协议对不对"切到"业务参数对不对"。

**业务规则 > 逆向技巧**：`"外部成员无法加入内部群聊"` 是服务端的规则，
逆向再完美也越不过。所以每次失败先分两类：

```
我们错了（格式/参数/顺序）  → 继续调
业务不允许（关系/权限/额度）→ 换参数或换目标，别硬试第四次
```

判别信号：errmsg 有明确语义 + 你已逐字节比过真请求 ⇒ 大概率是业务规则。

## 16.6 对照实验的顺序：先证伪最便宜的假设 ✅

定位 `-3066` 时，两个候选：①场景位（OBJ_ID 里的 `f4`）②成员 vid。正确顺序是**先做便宜的那个**：

| 步骤 | 成本 | 结果 |
|---|---|---|
| 只改场景位 `f4: 7 → 2`，其它不变 | 一次运行 | 仍是 `-3066` ⇒ 场景位**不是**原因，10 分钟证伪 |
| 检查成员 vid 的编解码 | 几分钟 | 用 varint **往返验证**（编码→解码→比对原值）排除编码器 bug |
| 换 vid 重跑 | 一次运行 | **当场成功** `RetCode: 0` |

关键细节：真正的原因不是"编码器有 bug"，而是**vid 取错了来源**——
那两个 id 是从"给客户的会话记录"里抠出来的（外部联系人），不是建群上下文里的内部同事。
正确来源：**一次真实建群的明文**（`f2` / `f3` 就是内部成员）。

> 教训：参数来源比参数格式更容易出错。**先问"这个值我是从哪抄的"，再问"我抄对了吗"。**

## 16.7 hotpatch stub：地址没错，但你看到的是桩 🟡

某关键函数在磁盘文件里的头几个字节是 `E9 xx xx xx xx`（`jmp rel32`），即被热补丁过。
`Interceptor.attach` 仍然可用（会跟到真实体），但：

- 静态反汇编看到的"函数体"是桩，别据此推断逻辑；
- 用**运行时读字节**确认（`Process.getModuleByName(...).base.add(RVA).readByteArray(16)`），
  而不是信静态工具的输出；
- 定位真实体：跟着 `jmp` 的目标走一步即可。

## 16.8 判据表与交付形态（配合 §13.10）✅

**成功/失败指纹**（写进脚本自动判读，不要人眼看日志）：

```
成功: HTTP 200 + RetCode: 0 + f7=0 + f9="ok"      （本批实测 CL:294 / f8=192）
格式: RetCode: -2003 + f9=""                       → 明文非法，先查注入回读
业务: RetCode: -3066 + 中文 errmsg                 → 参数/关系问题
没发: encoder 产物长度对不上任何 POST 的 CL         → 换载体（§16.2）
```

**交付形态**（与 13.10 一致，补两条本批新增）：

```
□ 载体等待时间做成参数（--wait），并在提示里写明"期间请在客户端点一下会话"
□ 每次运行按时间戳落盘完整证据（请求 + 解密后的响应），事后可用 report 脚本复判
```

**能力边界要写清楚**：本批是「自造载荷 + 复用客户端发送管道」，
既不是纯协议（T1），也不是调用业务函数（T2a）——它的代价是：客户端必须活着且已登录，
版本升级要重核 RVA 与结构体偏移。**交付文档里写清这一点，比多做一个功能更重要。**

## C.2 两种卡点的排查顺序（别弄反）

```
形态 A 型卡点：协议不懂
  1) 错误码 → 分组对照实验，一次只改一个字段
  2) 信封/必填字段：body 形状不要猜
  3) 前端 bundle 找调用点，拿真实参数样本

形态 B 型卡点：协议懂了也不动
  1) 回读注入点（afterHex 对不对）→ 不对就是注入没生效
  2) 长度指纹核对（encoder 产物长度 vs 线上 POST 的 Content-Length）→ 对不上就是没发
  3) 解响应读 errmsg → 有语义文案 = 已进业务层，改参数
  4) 前三条全过还失败 = 业务规则，换参数别硬试
```

**两类形态都在同一个位置栽过**：把「我没看到」当成「不存在」。
形态 A 是「没抓到 = 没有这个接口」，形态 B 是「服务端回 ok = 事情办成了」。
所以 §1.7 与 §14.7 那两条（受理 ≠ 完成、探针在跑 ≠ 探针有效）是通用底线，不是某一类目标的专属经验。

| 抓包只看到一个端点、body 是二进制 | 隧道式自研协议 | §15 三层次 → §16 全章（尤其 16.1/16.2） |

- 保留的真实细节只有**错误码数值**与**加密结构**——它们是可迁移的技术事实，不含产品身份。
